# Tests for conformance/generics

## Intent

This bundle exercises the **language reference** at
[`docs/language-reference/generics.md`](../../../../language-reference/generics.md).
The strategy is to enumerate every normative claim across the intro, Syntax, Description,
Type Parameter Packs, Pack queries, Pack count constraints, Type Checking, Parameter Binding
and Examples sections (see `## Claims` at the end), then give each claim at least one test
along the dimensions the doc commits to: basic case, pack-length boundaries (0 / 1 / 10),
declaration-form variants, and negatives for every rejection the doc states. Value
observations run on `COMPARE_COMPUTE -cpu` because generic specialization is resolved before
codegen and is therefore target-independent; three emission tests fan the monomorphized
result out over `hlsl / spirv-asm / glsl / metal / wgsl / cpp` so per-back-end codegen of a
specialized generic, a specialized generic struct and a specialized pack expansion stays
covered. Negatives use `DIAGNOSTIC_TEST` pinned to the diagnostic code the compiler actually
emits (`E30401`, `E30402`, `E30413`, `E30415`, `E30430`, `E30433`, `E30435`, `E30436`,
`E30437`, `E30438`, `E30104`, `E30105`, `E30440`, `E30442`, `E38029`, `E39999`). The doc's
new **Pack count constraints** section is covered end to end — accepting form, exact-count
mismatch, value-pack form, compile-time-expression right side, nested `countof(...)` right
side, orientation/operator restrictions, operand restriction, the oriented-proof rule and
the non-inference rule. `__first` / `__last` remain unshipped because they still crash the
compiler; that stays a finding plus an untested-claim row rather than a failing test.

## Claims

Flat enumeration of every normative claim in
[`generics.md`](../../../../language-reference/generics.md), grouped by doc section. Every ID
appears in `## Functional coverage` or `## Untested claims` above.

### Intro

- **C1**: A specialized generic is a concrete type or function that can be used like any other concrete type or function.
- **C2**: Generic parameters are bound explicitly, by inference, or by a combination of both.
- **C3**: A generic type alias can partially bind a generic's parameters, but doing so does not specialize the generic.
- **C4**: Value-typed arguments to generic parameters must be link-time constants.

### Syntax

- **C5**: A generic parameter list may be attached to a struct declaration.
- **C6**: A generic parameter list may be attached to an interface declaration.
- **C7**: A generic parameter list may be attached to a type alias declaration.
- **C8**: A generic parameter list may be attached to a function declaration in either the traditional or the `func` form.
- **C9**: A generic parameter list may be attached to a constructor (`__init`).
- **C10**: A generic parameter list may be attached to a subscript operator (`__subscript`).
- **C11**: A generic parameter list may declare zero parameters.
- **C12**: A generic value parameter is declared `let name [: type] [= init-expr]`.
- **C13**: A generic value parameter may instead be declared in the traditional `type name [= init-expr]` form.
- **C14**: A generic value parameter pack is declared `let each name [: type]`.
- **C15**: A generic type parameter is declared `[typename] name [: constraint] [= default-type]`.
- **C16**: A generic type parameter pack is declared `each name [: constraint]`.
- **C17**: A `where` clause may carry the `optional` modifier.
- **C18**: A `where` clause may declare `nonempty(P)`.
- **C19**: A `where` clause may declare `countof(P) == expr`.
- **C20**: A conformance constraint may name several constraining types separated by commas.
- **C21**: An equality constraint is written `== simple-type-spec`.
- **C22**: A coercion constraint is written `(simple-type-spec) [implicit]` and is usable only in generic extensions.
- **C23**: Generic enumeration declarations parse but are not currently useful.

### Description

- **C24**: A generic value parameter's type must be Boolean, integer, or an enumeration.
- **C25**: A value parameter pack is a variable-length list of values of a single declared type.
- **C26**: A type parameter pack is a variable-length list of types.
- **C27**: An inline `TypeParam : ConstrainingType` constraint adds a single conformance requirement.
- **C28**: With an `optional` conformance or equality constraint, `ParamType is ConstrainingType` is true when the parameter conforms to or equals the constraining type, and inside `if (ParamType is ConstrainingType)` a value of the parameter type may be used as the constraining type.
- **C29**: A constraint on a type parameter pack applies to every type in the pack.
- **C30**: Packs may be constrained with `where nonempty(P)`, requiring the pack to be non-empty at specialization time.
- **C31**: Packs may be constrained with `where countof(P) == IntExpr`.
- **C32**: Value parameters that are not packs cannot be constrained.
- **C33**: A conformance requirement's constraining type must be an interface that the parameter has as a base, directly or transitively.

### Type Parameter Packs

- **C34**: When a generic construct is specialized, a possibly-empty sequence of type arguments is bound to a type parameter pack.
- **C35**: There must be at least one each-expression within an expand-expression.
- **C36**: An each-expression must always be enclosed within an expand-expression, except in a generic type declaration.
- **C37**: An expand-expression evaluates to a comma-separated sequence of length N, with every embedded each-expression replaced by the Nth element of its pack.
- **C38**: If multiple each-expressions appear in one expand-expression, the referenced packs must have equal length.
- **C39**: A function parameter list may declare multiple expand/each parameters, whose packs must have equal lengths.
- **C40**: In function parameter lists, expand/each constructs must come after all other parameters.

### Pack queries

- **C41**: `__first(P)` and `__last(P)` are partial operations requiring `P` to be known non-empty, which `where nonempty(P)` provides.
- **C42**: `__trimFirst(P)` and `__trimLast(P)` are total operations and yield an empty pack when applied to an empty pack.
- **C43**: The operand of `nonempty(...)` must be a direct reference to a pack parameter declared in the current generic declaration.
- **C44**: `optional nonempty(...)` is parsed but rejected as invalid.

### Pack count constraints

- **C45**: `where countof(T) == N` requires the pack `T` to have exactly `N` elements at specialization time.
- **C46**: The operand of the left-side `countof(...)` must be a direct reference to a pack parameter declared in the current generic declaration.
- **C47**: The right side of a pack count constraint must be a compile-time integer expression.
- **C48**: Pack count constraints are oriented: `N == countof(T)`, `countof(T) != N` and `countof(T) >= N` are not pack count constraints.
- **C49**: A right-side expression may itself use `countof(...)`, letting an inner generic require the same count as an outer pack.
- **C50**: `countof(D) == countof(TIndex)` is not equivalent inside `inner`, because the left-side pack `D` is not declared by `inner`.
- **C51**: A declared `countof(T) == countof(U)` constraint can satisfy a callee requirement about `T`, but is not used backwards to satisfy a requirement about `U`.

### Type Checking

- **C52**: Type checking of parameterized types happens before specialization; an operation is legal only if it is legal for all concrete types conforming to the declared constraints.
- **C53**: A type equality constraint `T == U` makes `T` be `U` for all intents and purposes.
- **C54**: A type conformance constraint `T : U` makes `T` conform to `U`, implementing all of its requirements.
- **C55**: A type constraint `U(T)` allows `T` to be converted to `U`.
- **C56**: Type constraints may be declared for type expressions that include generic type parameters, such as `where T.AssocT == int`.
- **C57**: Pack count constraints are checked as exact shape requirements: during specialization `countof(P)` must equal the expected compile-time integer value.
- **C58**: No assumptions are made about generic value parameters other than their declared type.

### Parameter Binding

- **C59**: In explicit binding the arguments are listed in angle brackets after the generic type or function identifier.
- **C60**: Explicit binding cannot be used in constructs that do not use a named identifier at call sites.
- **C61**: In implicit binding the arguments are inferred by matching the generic parameters against call-site argument expressions, and it is an error when an argument cannot be inferred.
- **C62**: When inference is ambiguous over fundamental scalar types or vectors of the same length, the element type with the highest promotion rank wins, ranked `int8_t`, `uint8_t`, `int16_t`, `uint16_t`, `int32_t`, `uint32_t`, `int64_t`, `uint64_t`, `float`, `double`.
- **C63**: A fundamental type is promoted to a 1-dimensional vector if necessary.
- **C64**: In all other cases, an ambiguous generic type argument is an error.
- **C65**: It is an error when inference yields multiple options for a generic value argument.
- **C66**: Pack count constraints do not infer generic value arguments.
- **C67**: Mixing explicit and implicit binding is allowed: the leftmost generic parameters use the provided arguments and the rest are inferred.

### Examples

- **C68**: A generic struct with type and value parameters can be specialized and its array field read per element.
- **C69**: A generic type alias can fix one parameter of a generic struct and leave the rest open.
- **C70**: A generic function taking an `IFunc<T, T, T>` parameter can be called with a concrete struct implementing it.
- **C71**: A generic constructor `__init<T : IInteger>` can initialize a struct from two values of type `T`.
- **C72**: A generic subscript `__subscript<T>(T i) where T : IInteger` serves both `get` and `set` for any `IInteger` index type.
- **C73**: A `where T : IArithmetic` constraint enables `+` on values of `T` inside the body.
- **C74**: An optional constraint with `if (T is IInteger)` selects behaviour per specialization.
- **C75**: A `where T.PropertyType == int` constraint admits a conformer whose associated type is `int` and rejects one whose associated type is `float`.
- **C76**: A generic extension may carry a coercion constraint such as `where int(A)`.
- **C77**: A type parameter pack expands with `expand`/`each` into one call per element.
- **C78**: Two function parameter packs of equal length expand pairwise.
- **C79**: Two generic extensions with different constraints each contribute their method only to the matching specialization.
- **C80**: An un-inferable return-type parameter can be bound explicitly while the remaining parameters are inferred.
- **C81**: A type parameter and a value parameter can both be inferred from one fixed-size array argument.
- **C82**: A value parameter that would need two different values from two arguments cannot be inferred.
- **C83**: An ambiguous non-fundamental type inference is resolved by explicit binding.
