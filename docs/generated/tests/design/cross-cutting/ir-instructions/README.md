# Tests for design/cross-cutting/ir-instructions

## Intent

This bundle exercises the **observable shape of the Slang IR** as
catalogued in
[ir-instructions.md](../../../../design/cross-cutting/ir-instructions.md). The
doc's per-family tables are **representative, not exhaustive**, so the
coverage strategy is one test per opcode (or per opcode pair) that the
overview actually names: compile the obvious source construct that ought
to produce it and FileCheck the `LOWER-TO-IR` dump for the opcode, with a
`-target` emission fan-out for the rows whose consequence the doc states
in terms of generated code (`imageLoad`/`imageStore`, atomics, barriers,
wave intrinsics, `MetalPackedVec`, the `glslFragDepth*` decorations, the
work-graph `nodeLaunch` string operand). Rows that are synthesized inside
target legalization — `ImageTexelPointer` is the one here — are observed
in the emitted SPIR-V instead, because they are not in the pre-legalization
dump. Every `-dump-ir` test feeds its arithmetic non-constant operands
(`uniform` globals or `SV_DispatchThreadID`) and sinks results into a
buffer, so neither the constant folder nor DCE can remove the instruction
before the CHECK sees it. Per-opcode catalog detail belongs to the
`ir-reference/*` bundles and individual pass behaviour to
`pipeline/05-ir-passes`; this bundle stays at the "which opcode does this
construct produce, and what does it become on each target" level.

- H2 — `Global` is always hoisted to module scope but, unlike `Hoistable`, never deduplicated. _(untested — internal-source-fact)_

- H5 — Hoistable emitters are named `get*` rather than `emit*` because they may return an existing inst. _(untested — internal-source-fact)_

## Sibling-bundle overlap

The per-family opcode catalog — every opcode in a family with its operand
shape, op-flags and AST origin — is owned by the `ir-reference/*` bundles
(`types`, `values`, `control-flow`, `structure`,
`generics-and-existentials`, `resources-and-atomics`, `decorations`,
`differentiation`, `metadata`, `misc`). This bundle deliberately tests
only the opcodes the `ir-instructions.md` overview itself names, to avoid
duplicating that catalog-level coverage. Module read/write and the
`Unrecognized` stable-name fallback belong to `cross-cutting/serialization`;
the behaviour of individual IR passes belongs to `pipeline/05-ir-passes`.
