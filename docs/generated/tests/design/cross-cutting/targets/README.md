# Tests for design/cross-cutting/targets

## Intent

This bundle exercises the target model described in
[`docs/generated/design/cross-cutting/targets.md`](../../../../design/cross-cutting/targets.md):
which output formats the compiler can select, how capability atoms
combine into compatible and incompatible sets, how a profile pins a
stage plus a feature-level version without pinning a format, and the
two places where target choice shows through into emitted code
(`__target_switch` specialization and target-specific legalization).
The coverage strategy is one positive test per documented claim plus a
negative for every documented rejection, with the positive tests fanned
out across every text-emit target the claim is observable on
(`hlsl` / `glsl` / `spirv-asm` / `metal` / `wgsl` / `cuda` / `cpp`) and
the boundary axes the doc names instantiated per family: the floor and
the top of each version family, the arm-count edges of a target switch,
and the "profile supplies no version" edge of the capability-set
fallback. Per-target _emitter_ behaviour — how one construct is spelled
in one language — belongs to the `target-pipelines/*` bundles, which
this document explicitly hands off to, so it is recorded under
`## Untested claims` rather than tested twice.

## Claims

Numbered enumeration of the claims extracted from the source document.
Every claim is either covered above or listed as untested.

**`## Targets`** — C1 each documented text-emit backend produces
target-shaped text; C2 the SPIR-V group exposes binary and assembly
variants of one backend; C3 the C++ and CUDA groups expose header
variants that emit a declarations-only file; C4 `SLANG_HOST_CPP_SOURCE`
is host-side C++ from the same C++ backend; C5 the public target set is
closed, so an unknown `-target` name is rejected; C6 the Slang
round-trip row has no public target and no `CodeGenTarget` value; C7
DXBC / DXIL come from FXC / DXC downstream; C8 metallib comes from
Metal's downstream tools; C9 WGSL→SPIR-V goes through WGSL; C10 PTX and
CUDA object code come from NVRTC / nvcc; C11 the CPU-binaries group is
LLVM or a downstream C++ compiler; C12 the VM row emits interpreter
bytecode; C13 the Torch row emits a PyTorch binding; C14 the deprecated
GLSL enumerators are retained but removed; C15 `SourceLanguage` is the
input flavour.

**`### Vocabulary`** — C16 a capability name is a disjunction of
conjunctions of atoms; C17 `target` and `stage` are distinct keyholes
populated by key atoms; C18 a version family is a chain ordered by
inheritance; C19 a leading underscore marks an internal name.

**`### Definition forms`** — C20 the three declaration forms; C21 each
family carries a `*_latest` alias naming its highest version; C22 `+`
is incompatible when both sides populate one keyhole differently; C23
`|` creates an alternative; C24 an unpopulated keyhole is compatible
with any key atom of that keyhole; C25 an extension atom records its
version floor by inheritance and the enabled capability inherits from
the extension; C26 two spellings sharing a floor stay interchangeable.

**`### Runtime representation`** — C27 the join of two capability sets
decides whether an entry point satisfies a function's requirements; C28
minimum-requirement inference belongs to a late IR pass; C29 the atom
classifiers.

**`### Auto-generated reference`** — C30 the `///` harvest rules and the
six `[GROUP]` headings; C31 the doc comment must sit on the public
alias; C32 `[Compound]` aliases gate user-visible builtins against the
active target and stage, including the compute-class restriction of

**`## Profiles`** — C33 a profile pins a stage plus a version and does
not carry a format; C34 profile names are a closed set; C35 a profile's
stage conflicts with a differing explicit `-stage`; C36 the target
keyhole is chosen first and profile atoms are admitted only where

**`## How target choice affects IR`** — C43 `[target]` / `[stage]`
