# Tests for design/name-resolution/visibility

## Intent

This bundle exercises the declaration-visibility rules described in
[`docs/generated/design/name-resolution/visibility.md`](../../../../design/name-resolution/visibility.md):
which decl/scope pairs `isDeclVisibleFromScope` admits, which pairs are
rejected with `declaration not accessible` (30600) at the lookup boundary or
during overload resolution, which declarations `checkVisibility` rejects
outright (higher-than-parent 30601, invalid-private 30603, less-visible-type
30604, misplaced modifier 36005, duplicate modifier 31202), and how a decl
that carries no visibility keyword is classified.

The strategy is a **positive/negative pair per enforcement claim**: one test
proving access is permitted from the scope the keyword allows, one proving
the same access is rejected from a scope it forbids. Positive cases run under
`//TEST:INTERPRET(filecheck=CHECK):` (or `//TEST:SIMPLE ... -target hlsl`
when the claim needs a `-std` selection, which `slangi` does not accept);
negative cases use `//DIAGNOSTIC_TEST:SIMPLE(diag=CHECK):` with caret columns
copied from the runner's "Suggested annotations". Visibility is resolved at
semantic check before any target lowering, so there is no per-backend
emission fan-out — the one exception is the auto-diff synthesis claim, which
needs a runtime observation and therefore uses `COMPARE_COMPUTE -cpu`.

Two axes new to this revision of the doc get dedicated version-paired tests:
the **Slang 2026 aggregate-inheritance rule** (an unmodified member of an
aggregate inherits the aggregate's effective visibility), tested at both
`-std 2025` and `-std 2026` with the same source so the version gate itself
is the observation, and the **split visibility of synthesized extensions**
(a `private` `[Differentiable]` member's derivative extension must be
`internal`, not `private`).

The bundle is deliberately **single-file**: cross-module claims (`internal`
invisible from another module, `__exported import` re-export, the
`isOwnModuleOrIncludedFileScope` non-transitivity rule) cannot be expressed
in one `.slang` source and are recorded under `## Untested claims`.
`_repro/` holds a non-test reproduction referenced by a filed finding; it
carries no `//TEST` directive and is skipped by the runner.

## Claims

Enumerated per [`_claims.md` §1](../../../_meta/prompts/_claims.md), grouped by the
doc's own headings. The page mixes user-observable visibility rules with a
layer of internal compiler structure (the `DeclVisibility` enum, the modifier
classes, the `getDeclVisibility` walk, the `getTypeVisibility` memo), so the
list is split: the **user-observable** claims are the ones a `.slang` file or
a `slangc` invocation can reach, and the **internal-source facts** at the end
are C++-level statements whose observable consequence is already carried by a
user-observable claim; those are classified in the untested table below.

User-observable claims:

1. A `module` declaration carries no version of its own: `languageVersion` is initialized from the compile request's `LanguageVersion` option, and the parser then upgrades a legacy value to 2025 when the file uses a modern construct that requires it.
2. `SLANG_LANGUAGE_VERSION_LEGACY` is `2018`, and `SLANG_LANGUAGE_VERSION_DEFAULT` is that legacy value, so the documented language default is still 2018.
3. The misspelled `SLANG_LANGAUGE_VERSION_DEFAULT` is retained beside the correct spelling purely for source compatibility.
4. The visibility defaults depend only on the module's resolved `languageVersion`; `SlangGlobalSessionDesc::minLanguageVersion` records a preferred floor and is not consulted by the visibility-classification path.
5. `public`: visible from any module that has imported the declaring module.
6. `internal`: visible only inside the declaring module, including all of its files.
7. `private`: visible only inside the declaring aggregate type (`struct`, `class`, `interface`, ...).
8. A namespace is not a legal container for `private`: a namespace member is still a global decl, so `private` on it is rejected at the declaration site with `invalid-use-of-private-visibility`.
9. For an `AccessorDecl` or `EnumCaseDecl`, visibility is inherited from the enclosing decl.
10. For a `GenericDecl`, visibility is taken from its `inner` decl.
11. For a generic parameter or `GenericTypeConstraintDecl` whose parent is a `GenericDecl`, visibility is that generic's inner decl's visibility; a `GenericTypeConstraintDecl` with any other parent falls back to `Default`.
12. Slang 2026 and later: an unmodified member of an aggregate inherits the aggregate's effective visibility, so in `internal struct S { void f(); }` the method `f` is `internal` rather than picking up the module default.
13. The 2026 rule is keyed off the aggregate's effective visibility, so it composes transitively through nested aggregates.
14. The 2026 rule applies only when the module's `languageVersion` is at least 2026, so existing 2025 and legacy code keeps the older behaviour.
15. A member of an interface inherits the interface's visibility.
16. Otherwise the visibility is the module's default.
17. The legacy language treats every unannotated decl as `public`.
18. Modern versions default to `internal` unless the module is marked `public` at the top: `checkModule` flips the module-wide default to `public` when it finds a `PublicModifier` on the `ModuleDecl`.
19. `NamespaceDecl` is unconditionally `Public`.
20. Nothing in the fall-back chain is conditioned on a decl being a member of anything, so a function-local `VarDecl` takes the module default like any other unmodified decl and `checkVisibility` runs on it.
21. In a module declared `public module M;` a local is therefore `public`, so the container-level cap rejects a local whose type is `internal` with `use-of-less-visible-type` (30604) even though the name never escapes the function.
22. Lookup boundary: if lookup returned candidates but the visibility filter removed all of them, `filterLookupResultByVisibilityAndDiagnose` emits `decl-is-not-visible` (30600) and reports the first offending decl.
23. In language-server mode the same function intentionally returns the unfiltered result so completion can keep operating.
24. Overload resolution: `TryCheckOverloadCandidateVisibility` runs on every survivor of the arity / type checks; in `JustTrying` mode it silently drops the candidate, and in `ForReal` mode it emits the same `DeclIsNotVisible` diagnostic.
25. `Public` is always visible.
26. `Internal` is visible iff `getModuleDecl(decl)` equals `getModuleDecl(scope)` — the requesting scope is part of the same module.
27. `Private` is visible iff one of the requesting scope's parents is the enclosing aggregate that owns the decl, or the scope is inside an `ExtensionDecl` whose target type matches.
28. When the candidate lives in an `ExtensionDecl` the predicate resolves the extension's target type and compares it with the requesting scope's enclosing aggregate, so `extension S { private foo() {...} }` works from inside `S` and from another extension on `S`, even a generic extension that specializes to `S`.
29. That specialization step is guarded on the candidate's own container being an `ExtensionDecl`, so a `private` member declared in the body of a generic type `G<T>` is reachable from neither `extension G<int>` nor `extension<T> G<T>`; only a `private` declared in an `extension` crosses instantiations.
30. `getTypeVisibility` takes the minimum of the underlying decl's visibility and the visibilities of its declaration-reference generic arguments, so `HashMap<String, InternalKey>` is effectively `internal` even if `HashMap` is `public`.
31. `checkVisibility` rejects a decl that references a type less visible than itself with `use-of-less-visible-type` (30604).
32. `checkVisibility` also caps a decl's visibility at that of the nearest enclosing `AggTypeDeclBase`; the search starts at the decl itself, so an aggregate is compared against itself and the cap effectively bites on non-aggregate members. Violations are `decl-cannot-have-higher-visibility` (30601).
33. `extern` and `export` are distinct from the visibility classification and do not change a decl's `DeclVisibility`.
34. `DeclPassesLookupMask` always drops `ExtensionExternVarModifier` decls from lookup, and drops an `ExternModifier` member whose parent is an `ExtensionDecl`, so those `extern` members are hidden from lookup regardless of their visibility keyword.
35. `extension S { extern int extra; }` is reported as `missing-original-defintion-of-extern-decl` (31143) at the declaration and `no-member-of-name-in-type` (30027) at the use site — not the `decl-is-not-visible` (30600) a visibility rejection would produce.
36. `HLSLExportModifier` — the bare `export` keyword — records linkage intent and does not by itself raise a decl's `DeclVisibility`.
37. `isModuleReachableViaExportedImports` follows only imports marked `ExportedModifier`, so an `__exported import` re-exports the imported module while a plain `import` does not.
38. `isOwnModuleOrIncludedFileScope` admits a module's own scope and a `FileDecl` whose `parentDecl` is that same module as its re-export surface.
39. The `parentDecl == moduleDecl` conjunct is load-bearing: a foreign module's `FileDecl` points at that module and is dropped no matter how it arrived on the chain, which is what keeps a plain `import` non-transitive.
40. The same predicate drops `using`-spliced namespace siblings, so a primary file's `using namespace Foo;` does not leak through an `import`.
41. A generic parameter is never independently more or less visible than the decl it parameterizes.
42. Requirement-satisfaction synthesizers give a synthesized member `Min(parentVisibility, requirementVisibility)` when the satisfied requirement carries an explicit visibility modifier, so it is never more visible than either its parent or the requirement.
43. Synthesized differential types and fields propagate the parent member's visibility directly.
44. `getSynthesizedExtensionVisibility` returns a pair with separate `extensionVisibility` and `memberVisibility` fields, because an extension is hoisted to module scope where `private` is not a legal visibility at all.
45. `Public` and `Internal` targets map both fields to themselves; a `Private` target maps the extension to `Internal` while keeping the synthesized members `Private`, so the callable's API surface is unchanged.
46. A decl carrying `IgnoreForLookupModifier` is skipped by lookup before visibility filtering even sees it, so visibility rules never apply to it; the only producer today is the enum tag-type inheritance decl.
47. `public` inside an `internal` struct is rejected: `decl-cannot-have-higher-visibility` fires at the inner decl.
48. `invalid-use-of-private-visibility` (30603) fires at the declaration site for three shapes, not just the top-level one: a module- or file-scope decl, a member of a `namespace`, and an interface requirement.
49. `invalid-visibility-modifier-on-type-of-decl` (36005) fires when the user marks a namespace `internal`, or otherwise attaches a visibility modifier to an unsupported node kind.
50. `private namespace X` does not reach 36005: the `isGlobalDecl` test runs first, so a namespace — top-level or nested — is reported as 30603 instead.
51. A repeated modifier such as `public public ...` is caught by the conflict-group check, which emits `duplicate-modifier` (31202).
52. A `public func foo(x: InternalT)` produces `use-of-less-visible-type` (30604).
53. Cross-language-version import: the modern module's decls are still classified by their own `defaultVisibility`, being in a different module makes `internal` decls invisible regardless of the caller's language version, and the legacy module's own decls are seen as `public` by any caller.
54. When auto-diff synthesizes a derivative as an `extension` on a function-as-type whose owner is itself a struct member, `isDeclVisibleFromScope` resolves the parent aggregate recursively so the derivative inherits the ordinary member's visibility scope.
55. A `using` declaration only brings a namespace-like container into scope; `visitUsingDecl` requires its argument to resolve to a `NamespaceDeclBase` and otherwise emits `ExpectedANamespace` (30061), so `using SomeStruct;` is rejected rather than aliasing the struct.
56. A `using` does not re-export an individual `internal` member, so there is no `using`-specific visibility rejection.
57. A `public` `FuncAliasDecl` whose target is not `Public`, or whose target's module is reachable only through a plain non-`__exported` `import`, is rejected with `public-custom-derivative-uses-non-exported-import` (31162).
58. A `FuncAliasDecl` is never written by hand: it is synthesized by the AD-2.0 translation of a `[ForwardDerivative(...)]` or `[BackwardDerivative(...)]` attribute, which builds an extension on the primal-function-as-type with an alias member naming the supplied derivative.
59. The rejected shape is therefore a `public` primal whose derivative comes from a plainly imported module.

Internal-source facts (enum values, modifier classes, and helper plumbing; no independent user-observable consequence):

60. `VisibilityModifier` has exactly three concrete subclasses — `PublicModifier`, `PrivateModifier`, `InternalModifier` — each an empty marker class.
61. `DeclVisibility` has values `Private`, `Internal`, `Public` plus the alias `Default = Internal`, ordered `Private < Internal < Public`, and `Math::Min` over them computes a composite's effective visibility.
62. `ModuleDecl::defaultVisibility` is initialized to `Internal` at declaration time and overridden during semantic checking.
63. The classification formula is `defaultVis = languageVersion == LEGACY ? Public : parentModule->defaultVisibility`.
64. `getDeclVisibility` walks `decl->modifiers` and returns the first `VisibilityModifier` it finds.
65. Any `DeclVisibility` value other than the three named ones — the impossible `Default` after enum lookup — is treated as not visible.
66. `_getTypeVisibility` threads a `Dictionary<Type*, DeclVisibility>` memo through the walk and caches only completed results, so a repeated generic argument such as `Pair<T, T>` is not re-traversed.
67. A `getSynthesizedExtensionVisibility` target that is neither `Public`, `Internal`, nor `Private` is `SLANG_UNEXPECTED`.
68. `getMoreRestrictiveVisibility` computes the pairwise minimum of two visibilities after normalizing `Default`.
