# Tests for name-resolution/scopes

## Intent

This bundle exercises the lexical-scoping rules described in
[`docs/generated/design/name-resolution/scopes.md`](../../../../design/name-resolution/scopes.md):
which AST nodes introduce a fresh `Scope`, what is reachable from which
point in the source, how lookup walks the parent chain plus the sibling
chain, and the documented edge cases (per-decl hiding inside a block,
extension-member exclusion, generic-parameter isolation, namespace
reopening, `using`-decl sibling wiring, the synthesized `This` member of
an interface, interface constraint placement, deferred body parsing, and
the `if (let ...)` synthetic scope).

Scoping is not directly observable, so every claim is translated into
name resolution: either **a name resolves to the declaration the doc
says it does** — a positive `//TEST:INTERPRET` whose `printf` echoes a
value that only a correct binding can produce — or **a name is not in
scope at a given point** — a `//DIAGNOSTIC_TEST:SIMPLE(diag=CHECK)`
pinning `undefined identifier` (E30015) at the use site with
caret-anchored annotations. Each scope kind that the doc's
"Scope-bearing AST nodes" table names and that has a surface syntax gets
both halves: a positive that resolves a name inside the scope, and a
negative that proves the same name is not visible just outside it, since
the boundary is what the doc is mostly about.

Multi-backend rule: every claim on this page is fixed at semantic check,
before any target-specific lowering, so each test carries a single
directive and there is no per-target emission fan-out. No test needs a
GPU.

## Claims

Enumerated per [`_claims.md` §1](../../../_meta/prompts/_claims.md), grouped by the
doc's own headings. This page is half user-observable scoping rules and half
internal compiler structure (the `Scope` record's fields, the parser's
`currentScope` bookkeeping, and the `Decl`-subclass hierarchy behind
`ownedScope`), so the list is split: the **user-observable** claims below are
the ones a `.slang` file can reach, and the **internal-source facts** at the
end are class-layout and parser-plumbing statements whose only observable
consequence is already stated by a user-observable claim — those all land in
the untested-claims table below with reason `internal-source-fact`.

User-observable claims:

1. `ModuleDecl` owns a scope, so a file-scope declaration is reachable from any function in the file.
2. `NamespaceDecl` owns a scope, so its members are not reachable from the enclosing module scope without qualification.
3. `FileDecl` owns a scope per source file of a module.
4. `AggTypeDecl` and its subclasses (`StructDecl`, `ClassDecl`, `InterfaceDecl`, `EnumDecl`, ...) own a scope holding their members.
5. `ThisTypeDecl` is the synthesized member of an `InterfaceDecl` representing the abstract `This` type, and it is never pushed as a parser scope.
6. `ExtensionDecl` owns a scope.
7. `GenericDecl` owns a scope, and that scope contains the generic parameters.
8. `CallableDecl` and its subclasses (`FuncDecl`, `ConstructorDecl`, `SubscriptDecl`, `AccessorDecl`, `FuncAliasDecl`) own a scope containing the parameter decls.
9. `PropertyDecl` owns a scope.
10. `BlockStmt` always gets a fresh `ScopeDecl` pushed by `parseBlockStatement`.
11. `ForStmt` gets a pushed `scopeDecl`, but `UnscopedForStmt` reuses the parent scope for HLSL compatibility.
12. `WhileStmt` / `DoWhileStmt` get no fresh `ScopeDecl` from the parser; the loop body owns its own scope only when it is a `BlockStmt`.
13. `SwitchStmt` gets no assigned `scopeDecl`; `ParseSwitchStmt` gives the body one scoped `BlockStmt` instead.
14. A `CatchStmt` handler is parsed inside a fresh `ScopeDecl` pushed by `ParseDoCatchStatement`.
15. `parseIfLetStatement` pushes a fresh `ScopeDecl` for the unwrapped variable of `if (let x = ...)`.
16. `LambdaExpr` owns a dedicated `ScopeDecl` for its parameter list; the scope belongs to the expression, not to `LambdaDecl`.
17. `IfStmt` does not own a scope; its branch bodies parse as `BlockStmt`s that own one.
18. `SeqStmt`, `DeclStmt`, and other non-`ScopeStmt` statements simply live inside the enclosing scope.
19. A declaration used directly as the body of a statement that owns no scope - `while (c) int x = 1;`, and the same shape under `do` or `if` - is accepted rather than rejected, and the name leaks into the enclosing container.
20. Only a `{ ... }` body isolates such a declaration, because only the `BlockStmt` pushes a `ScopeDecl`.
21. A local declared under one `case` label of a plain `switch` is still in scope in textually later cases of the same `switch`, and out of scope after it.
22. `__target_switch` and `__stage_switch` push and pop a `ScopeDecl` around each case group, so a local declared in one case is not visible from any other case of the same statement.
23. A lambda parameter is visible throughout the body - block form or single-expression form - and undefined once the expression ends.
24. Sibling-scope use 1: a module split across several `__include`d files gets one `FileDecl` per file attached as a sibling of the module's scope, so lookup inside the module sees the union of all files' members.
25. Sibling-scope use 2: when module B imports module A, the checker adds A's scope as a sibling of B's scope so A's names are reachable in B without qualification.
26. `isOwnModuleOrIncludedFileScope` admits only A's own scope and `FileDecl`s parented to A, so a `using namespace Foo;` written in A, or a module C that A merely `import`ed, does not leak into B - a plain `import` is not silently transitive.
27. In the three-module example (C declares `namespace Foo`; A does `import C; using namespace Foo;`; B does `import A;`), B sees A's own members and A's `__include`d files' members, but not `Foo`'s members unqualified and not C's.
28. Writing `__exported import C;` in A is what makes C reachable from B, because `importModuleIntoScope` recurses into nested `import`s carrying the `ExportedModifier`.
29. Sibling-scope use 3: re-declaring `namespace Foo {}` reuses the existing `NamespaceDecl` and the checker links the declarations as siblings.
30. Sibling-scope use 4: a `using` declaration splices the named namespace's owned and sibling scopes into the `using` decl's scope, so the namespace's members become reachable without qualification.
31. When two scopes on the same sibling chain supply the same name, neither wins by position: both declarations land in one `LookupResult`.
32. Overloadable declarations found that way form an overload set that overload resolution ranks; anything else remains an `OverloadedExpr` whose use site is reported as `AmbiguousReference`.
33. Implicit scope: the generic parameter list lives in the `GenericDecl`'s scope, pushed before the inner decl is parsed, so the inner decl's own scope is its child.
34. Implicit scope: `ExtensionDecl` owns a scope, but the members of the type it extends are not in the extension's scope chain - they are reached through member lookup at check time.
35. Implicit scope: `InterfaceDecl` owns a single scope for its requirements, and default-impl bodies parse against a derived `InterfaceDefaultImplDecl` that has its own scope.
36. An associated type's constraint clause does not go into the `AssocTypeDecl`'s own scope; `associatedtype A : IBar` puts its `GenericTypeConstraintDecl` in the enclosing interface as a sibling member of the associated type.
37. `associatedtype A where A : IBar` places its constraint the same way.
38. The dedicated `__constraint` keyword inserts a `GenericTypeConstraintDecl` directly into the interface scope the same way, so all three surface forms land in one scope as parallel requirement members.
39. Implicit scope: `if (let x = ...)` creates `ScopeDecl`s for the temporary `$OptVar` binding and for the user-visible unwrapped variable inside the positive branch.
40. Lookup step 1: visit `currentScope` itself - its `containerDecl`'s direct members.
41. Lookup step 2: walk `currentScope->nextSibling` until null, repeating step 1 for each sibling.
42. Lookup step 3: move to `currentScope->parent` and repeat from step 1.
43. Lookup step 4: stop when the parent chain reaches `nullptr`.
44. `findClosestInScopeName` reuses the same parent-then-sibling traversal, skipping the core module, to attach a "did you mean" suggestion to `UndefinedIdentifier`.
45. Edge case: a `BlockStmt` whose body contains zero declarations still has a fresh `ScopeDecl`, and the empty block gets an `EmptyStmt`.
46. Edge case: `Decl::hiddenFromLookup` engages only for blocks that contain declaration statements, and is cleared as the checker walks past each `DeclStmt`, so a block-local is invisible to a forward reference and to its own initializer.
47. Edge case: when the source language is HLSL, `ParseForStatement` builds an `UnscopedForStmt` and skips the scope push, so the `for` init variable leaks into the surrounding scope.
48. Edge case: `parseNamespaceDecl` reuses the first `NamespaceDecl` it finds in the parent, so all subsequent declarations parse into the same `ContainerDecl`.
49. Edge case: a reference to a generic type parameter `T` inside the inner decl resolves through the inner scope's parent, but a sibling of the outer decl that mentions `T` cannot reach it.
50. Edge case: a `GenericTypeConstraintDecl` is only allowed as a child of an `InterfaceDecl` (or of a `GenericDecl`); `isDeclAllowed` enforces the placement.
51. Edge case: a `__constraint` whose subject resolves to the bare `This` type is rejected with `ConstraintSubjectCannotBeThisType` and its subject is replaced with the error type.
52. Edge case: constraints on associated types (e.g. `This.A : IBar`) are permitted.
53. Edge case: lookup into a type that has an active extension must walk the extension's members explicitly; the extension scope is not a sibling of the extended type's scope.
54. Edge case: a `UsingDecl` captures `parser->currentScope` at parse time and the sibling injection happens at check time, so what checking changes is that captured scope's `nextSibling` chain, not the scope the names land in.
55. Edge case: if the `using` argument does not resolve to any namespace-like entity, no sibling is added and the checker diagnoses `ExpectedANamespace`.
56. Edge case: in the `Decl` parsing stage a function body is recorded as an `UnparsedStmt` capturing `currentScope` and `outerScope`, and `parseUnparsedStmt` restores exactly those, so a deferred body resolves names against the scope chain live at its declaration site.

Internal-source facts (class layout and parser plumbing; no independent user-observable consequence):

57. `Scope` is a three-field record - `containerDecl`, `parent`, `nextSibling` - whose `containerDecl` is deliberately an unowned pointer so a `Scope` cannot keep an AST node alive.
58. Every `ContainerDecl` carries an `ownedScope` field whose `containerDecl` points back to the owning decl.
59. `ScopeDecl` is a synthetic `ContainerDecl` with no surface syntax, created by the parser for any statement that introduces a local scope.
60. `ScopeStmt` is the abstract base of scope-owning statements and carries a single `ScopeDecl* scopeDecl`; the actual `Scope*` is `scopeDecl->ownedScope`.
61. `SemanticDecl` and `AttributeDecl` are direct `ContainerDecl` subclasses that own a scope via `ownedScope`.
62. `SynthesizedStructDecl`, `GLSLInterfaceBlockDecl`, `AssocTypeDecl`, and `GlobalGenericParamDecl` own scopes through the same `AggTypeDecl` mechanism.
63. `ThisTypeDecl` inherits the `ownedScope` field but the field stays null.
64. `CompileTimeForStmt` declares `ScopeStmt::scopeDecl`.
65. `GpuForeachStmt` declares `ScopeStmt::scopeDecl`.
66. `parseTargetSwitchStmtImpl` creates a per-case `ScopeDecl` rather than one on the statement.
67. The parser carries `currentScope`, `currentLookupScope`, and `outerScope`, and `PushScope` / `pushScopeAndSetParent` / `PopScope` all end in `resetLookupScope()` so the two scope pointers never drift apart.
68. Every parser path matches its push with a `PopScope` on the way out.
69. `addSiblingScopeForContainerDecl` allocates a fresh `Scope`, points it at the secondary `ContainerDecl`, and splices it into the destination scope's `nextSibling` list.
70. `FuncConstraintDecl` also lands in an interface or generic scope as a requirement member, but it is synthesized during header checking and has no parser path or scope of its own.
71. Pushing a `Scope` whose `containerDecl` is null is not supported; the bare-`Scope*` overload of `PushScope` exists only to restore a pre-built scope.
