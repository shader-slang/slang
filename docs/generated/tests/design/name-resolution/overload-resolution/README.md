# Tests for design/name-resolution/overload-resolution

## Intent

This bundle exercises the overload-resolution algorithm described in
[`docs/generated/design/name-resolution/overload-resolution.md`](../../../../design/name-resolution/overload-resolution.md):
the builtin-operator fast path that bypasses the resolver entirely for numeric
scalar / vector / matrix operands, the `TryCheckOverloadCandidate` probe-phase
filter pipeline (arity, fixity, types and coercion, directions, constraints,
visibility), the candidate families the probe phase draws from, the `ForReal`
finalize phase and the focused generic-inference diagnostics it selects, the
`ConversionCost` ranking and the conversions that have no named cost level, the
`CompareOverloadCandidates` tie-breaker (status, cost, lookup-result kind,
implicit-conversion preference, specificity, scope distance, overload rank),
partial generic application, the general path taken by operators the fast path
declines, and the documented failure modes.

Coverage strategy: one row per documented claim, with positive claims observed
through `//TEST:INTERPRET(filecheck=CHECK):` (an integer tag echoed by `printf`
names the overload that fired, or an overload probe reveals the type an
expression was given) and failure-mode claims pinned with
`//DIAGNOSTIC_TEST:SIMPLE(diag=CHECK):`. The conversion-cost table is treated as
an enumeration to expand rather than prose to summarize: each row that a pair of
user-written overloads can rank against a neighbouring row gets its own test,
and the rows that no user source can reach are classified in
`## Untested claims`. Boundary probes sit on the same anchor as their parent
claim: the adjacent pairs of the cost table (0 vs 400, 23 vs 400, 32 vs 400,
81 vs 400, 150 vs 400, 200 vs 300, 250 vs 400, 400 vs 450, 400 vs 500,
2 vs 10, 10 vs 410, 0 vs 30, 0 vs 400, 0 vs 500), the accumulated-cost sum past
the 900 implicit ceiling, the arity step's lower edge (defaults padding), upper
edge (too many) and unbounded edge (a variadic pack), and the 32-bit/64-bit and
signed/unsigned edges of the fast path's common-type rule.

Overload resolution is fixed at semantic check, so almost every test uses a
single target-independent directive. Two claims are exceptions and say so: the
GLSL-operator-scope carve-out needs `-allow-glsl` and therefore runs as
`COMPARE_COMPUTE -cpu`, and the parameter-group auto-dereference cost needs a
`ConstantBuffer` global that the interpreter cannot host, so it is observed in
emitted HLSL. One further test carries a `-std 2026` option because the claim it
pins is about a language-version boundary.

The source doc mixes user-observable rules with a description of the checker's
own structure (the `OverloadCandidate` fields, the filter-step function names,
the comparator's helper names). The enumeration below keeps the doc's own
wording for both, and the internal-structure statements that have no
`.slang`-visible consequence are classified in `## Untested claims` with reason
`internal-source-fact` rather than given tests.

## Claims

Enumerated per [`_claims.md` §1](../../../_meta/prompts/_claims.md), grouped by

### Concepts

1. `OverloadCandidate::Flavor` is one of `Func`, `Generic`, `UnspecializedGeneric`, `Expr`.
2. `OverloadCandidate::Status` progresses through `GenericArgumentInferenceFailed`, `Unchecked`, `ArityChecked`, `FixityChecked`, `TypeChecked`, `DirectionChecked`, `VisibilityChecked`, `Applicable`.
3. `OverloadCandidate::Flags` is a bitset holding only `IsPartiallyAppliedGeneric` today.
4. `explicitGenericArgCount` records how many leading ordinary generic arguments the caller supplied explicitly, starts at `-1`, and is handed to the generic constraint solver as a fixed prefix so a user-written argument is not overridden by a parameter default.
5. `GenericArgumentInferenceFailure::Kind` is one of `None`, `VariadicPackCountMismatch`, `GenericArityMismatch`, `OrdinaryGenericParamNotInferred`, `InterfaceConformanceNotSatisfied`, `GenericConstraintNotSatisfied`, `GenericParamUnificationConflict`.
6. `argMismatchArgIndex` / `argMismatchExpectedType` / `argMismatchActualType` record the first argument that failed to type-check, so a diagnostic can name the offending argument and both types rather than only the callee.
7. `OverloadResolveContext::Mode` is `JustTrying`, which silently rejects bad candidates, or `ForReal`, which emits a diagnostic for each rejection.
8. `ConversionCost` is an `unsigned int` whose `kConversionCost_*` levels sum across arguments.
9. `CoercionSite` is one of `General`, `Assignment`, `Argument`, `Return`, `Initializer`, `ExplicitCoercion`, and cost computation can vary per site.
10. Every `GenericArgumentInferenceFailure` payload is trivially copyable and the default constructor `memset`s the whole object, because candidates are copied inside standard-library algorithms.

### Probe phase: `TryCheckOverloadCandidate`

11. The probe pipeline runs arity, fixity, types, directions, constraints and visibility in that order and returns as soon as a step fails, leaving the candidate at the status of the last step it passed.
12. `TryCheckOverloadCandidateArity` accepts a call with fewer arguments than parameters when trailing defaults pad the count up to `allowed`.
13. A call below `required` is rejected, and in `ForReal` mode emits `Diagnostics::NotEnoughArguments`.
14. A call above `allowed` is rejected, and in `ForReal` mode emits `Diagnostics::TooManyArguments`.
15. An `allowed` of `-1` means unbounded, so a variadic callable accepts any count at or above `required`.
16. `TryCheckOverloadCandidateFixity` applies only to a `PrefixExpr` or `PostfixExpr` and requires the matching `PrefixModifier` / `PostfixModifier`, so `-x` does not bind to a postfix-only `operator-`; any other call form passes unconditionally.
17. `matchArgumentsToParams` pairs arguments with parameters and lets a brace initializer such as `f({1, 2})` be matched against a struct parameter instead of being rejected outright.
18. For `Flavor::Generic` the type step delegates to `TryCheckGenericOverloadCandidateTypes`, and when inference fails a separate `Flavor::UnspecializedGeneric` candidate carrying `Status::GenericArgumentInferenceFailed` is recorded so the failure can be diagnosed later.
19. In `ForReal` mode an explicit generic-argument list whose length falls outside the generic's allowed range gets `Diagnostics::GenericArgumentListArityMismatch`, and any other specialization failure gets `Diagnostics::CannotSpecializeGeneric`.
20. Only a too-short list reaches that arity diagnostic: `g<int, float, int>` on `int g<T, U>(T, U)` reports "too many arguments to call (got 3, expected 2)" from step 1 instead.
21. A too-short list lands on the generic-argument arity diagnostic only when the generic's inner declaration is not a `CallableDecl`; otherwise it becomes a partial generic application rather than an error.
22. For every argument the step calls `canCoerce(paramType, argType, arg.argExpr, &cost)` and accumulates the reported cost into `conversionCostSum`; when no coercion is possible the argument index and both types are recorded and the candidate is dropped.
23. When `context.disallowNestedConversions` is set the step demands `paramType->equals(argType)` instead of calling `canCoerce`, which is how the checker forbids stacking one user-defined conversion on top of another.
24. `TryCheckOverloadCandidateDirections` only checks the mutability of the implicit `this` parameter, rejecting a `[mutating]` method invoked on an immutable base with `Diagnostics::MutatingMethodOnImmutableValue`.
25. `TryCheckOverloadCandidateConstraints` validates `where`-clauses against the inferred substitutions and fills in generic arguments left to defaults, resolving them for an outermost generic through the `trySolveGenericArguments` fixpoint solver with the explicit ordinary prefix installed as fixed `CallerProvidedOrdinaryArg`s.
26. The solver's `solveCost` is deliberately not folded into `conversionCostSum`, because doing so would shift overload ranking and break ties that should stay ambiguous.
27. On solver failure the step falls through to the legacy per-constraint loop so `ForReal` mode can emit `Diagnostics::TypeArgumentDoesNotConformToInterface` for an unsatisfied conformance; nested generic applications keep the linear pass.
28. `TryCheckOverloadCandidateVisibility` delegates to `isDeclVisibleFromScope` and emits `Diagnostics::DeclIsNotVisible` in `ForReal` mode.
29. `TryCheckOverloadCandidateClassNewMatchUp` enforces the `new` / `class` pairing: a `NewExpr` whose candidate does not construct a `ClassDecl` gets `Diagnostics::NewCanOnlyBeUsedToInitializeAClass`, and a plain constructor call that does construct a class gets `Diagnostics::ClassCanOnlyBeInitializedWithNew`.
30. A candidate that survives every probe-phase step is tagged `Status::Applicable` with its total `conversionCostSum` populated.
31. `AddOverloadCandidateInner` removes every held entry the new candidate strictly beats, drops the new candidate when a held entry strictly beats it, and converts a unique best candidate into a two-element `bestCandidates` list on a tie.
32. Candidate tracking runs for every candidate, applicable or not, which is what lets the failure paths report the least-bad candidate rather than a bare "no overload".

### Probe phase: where candidates come from

33. `AddDeclRefOverloadCandidates` dispatches on the kind of declaration a `LookupResultItem` names: function aliases, callables, aggregate types, generics, typedefs, generic type parameters and function-valued parameters.
34. `AddFuncOverloadCandidate(LookupResultItem, DeclRef<CallableDecl>, ...)` contributes a single declared callable.
35. `AddCtorOverloadCandidate` contributes calls that go through a `ConstructorDecl`, with the result `Type` passed in.
36. `AddFuncOverloadCandidate(FuncType*, ...)` / `AddFuncExprOverloadCandidate` contribute first-class function values with `flavor == Expr`; a `ParamDecl` reaches that path only when its declared type is a `FuncType`, which source spells with `functype`.
37. `AddHigherOrderOverloadCandidates` contributes `__fwd_diff` / `__bwd_diff`-style operators that wrap a callee.
38. Each helper accepts a `baseCost` that `AddOverloadCandidate` adds to the candidate's accumulated cost; the ordinary lookup, function-value and higher-order entry points all pass `kConversionCost_None`, and today the only nontrivial `baseCost` is what `inferGenericArguments` reports.

### Finalize phase: `CompleteOverloadCandidate`

39. Once the probe phase finishes with exactly one best candidate, `CompleteOverloadCandidate` flips the mode to `ForReal` and re-runs the pipeline starting from `TryCheckOverloadCandidateClassNewMatchUp`, then arity, fixity, types, directions, constraints and visibility.
40. If the best candidate's status is `GenericArgumentInferenceFailed`, the recorded `genericInferenceFailure` selects a focused diagnostic, and only a `Kind::None` falls through to the blanket `Diagnostics::GenericArgumentInferenceFailed`.
41. Every inference-failure arm also emits a `Diagnostics::GenericSignatureTried` note rendered by `ASTPrinter::getDeclSignatureString`.
42. `Flavor::Func` and `Flavor::Generic` rebuild the callee with `ConstructLookupResultExpr`, which replays the item's breadcrumb chain; `Flavor::Func` then reuses `context.originalExpr` when it already is an `InvokeExpr`.
43. `Flavor::Generic` wraps the result in a `PartiallyAppliedGenericExpr` when the `IsPartiallyAppliedGeneric` flag is set, and otherwise builds a fully specialized generic decl-ref.
44. `Flavor::Expr` uses `candidate.exprVal` directly as the callee, with no `ConstructLookupResultExpr` step.
45. A `Flavor::UnspecializedGeneric` candidate never reaches the AST-construction switch, because its status is handled by the early error path.

### Conversion costs

46. Overload candidate probing computes each per-argument cost via `canCoerce` and accumulates the reported cost into the candidate's ranking sum.
47. An ambiguous conversion is deliberately reported as possible while probing and only fails when the checker asks for the coerced expression, at which point `Diagnostics::AmbiguousConversion` plus one `SeeDeclarationOf` note per tied initializer is emitted.
48. Two initializers with different parameter types can only tie at an explicit coercion site, because `_coerce` sets `disallowNestedConversions` everywhere else: `struct T { __init(int v) {} __init(uint v) {} }` with `T t = T(x)` on a `float` x is ambiguous.
49. Making the argument an `int` removes that ambiguity, because the exact match costs 0.
50. Writing `T t = x;` instead is an implicit site where neither initializer matches `float` exactly, so the failure is an ordinary type mismatch.
51. `canConvertImplicitly` allows anything cheaper than `kConversionCost_GeneralConversion` and rejects anything at or above it.
52. `kConversionCost_None` is 0 — identity.
53. `kConversionCost_GenericParamUpcast` is 1 — up-cast through a generic parameter.
54. `kConversionCost_LambdaToFunc` is 1 — lambda used where a `Func` value is expected.
55. `kConversionCost_UnconstraintGenericParam` is 20 — binding to an unconstrained generic parameter.

66. `kConversionCost_RankPromotion` is 150 — lossless promotion to a higher rank within the same conversion kind.

### Conversions that do not have their own cost level

92. `Optional<T>` to `Optional<U>` covariance recursively probes `T` to `U` and reports `innerCost + 1`, which keeps an exact match strictly cheaper than the covariant form.
93. A `ConstantBuffer<X>` / `ParameterBlock<X>` source is implicitly dereferenced to `X` at `kConversionCost_ImplicitDereference` before converting onward, so an overload on `ConstantBuffer<Foo>` still beats one on `Foo`.
94. Because that branch funnels all parameter-group coercion into the dereference path, a user-declared initializer that takes a parameter-group type is never considered by the conversion search.
95. `vector<T,4>` declares the `(vector<T,2>, T)` and `(T, vector<T,2>)` forms outright so overload resolution binds to them instead of promoting a scalar, and marks them `[deprecated]` and `[RemovedSince(2026, ...)]`.
96. Under the default language version `float4(f2, f)` still resolves to one of those forms, gets the legacy duplicate-the-scalar semantics, and reports the `[deprecated]` warning.
97. Compiling the module with language version 2026 or later turns the same call into an error instead, because `[RemovedSince]` fires and its message supersedes the deprecation one.
98. `createInvokeExprForExplicitCtor` type-checks the constructor against a temporary `DiagnosticSink` and forwards that sink's contents — including warning-severity output — to the real sink once it commits, skipping the forwarding when `outExpr == nullptr`.

### Short-circuiting a doomed conversion search

99. At a non-explicit coercion site `_coerce` returns failure immediately when `toType` is a scalar `BasicExpressionType` other than `bool` and `fromType` is a decl-ref to a `GenericTypeParamDeclBase`; `bool` and `DeclRefType` scalars such as `BFloat16` stay on the search path, and the guard changes no resolution outcome.

### Tie-breaking comparator

100. Step 1: a candidate with a higher `Status` wins, so an `Applicable` candidate is always preferred to an `ArityChecked` one.
101. Step 2: the lower `conversionCostSum` wins.
102. Step 3 `CompareLookupResultItems` prefers a concrete member over an interface requirement it satisfies.
103. Step 3 prefers a non-`extern` declaration over an `extern` one.
104. Step 3 prefers a non-extension declaration over an extension member, and an ordinary extension over a free-form one — an `extension` whose target type is a generic type parameter, spelled `extension<T : IFoo> T`.
105. Step 3 prefers any declaration over a module declaration and the more derived interface when both candidates are interface requirements, and returns "equal" outright when either candidate is a generic callable.
106. Step 4: if exactly one candidate is marked `ImplicitConversionModifier`, that one wins.
107. Step 5 `compareOverloadCandidateSpecificity` prefers the smaller `getSpecializedParamCount`, so a non-generic candidate beats a specialized generic one; variadicness and default-parameter counts are not consulted.
108. Step 6 `getExportRank` fires only when the left candidate carries `ExternModifier` and the right carries `HLSLExportModifier`, and then prefers the `extern` one.
109. Step 7: for non-generic flavors `getScopeRank` prefers the declaration at the shorter scope distance from the call site.
110. Step 8 `getOverloadRank` compares the `[OverloadRank(N)]` attribute — a declaration without it ranks 0 and the higher rank wins — and the attribute is declared `@internal`, with `core.meta.slang` / `hlsl.meta.slang` its only users in the tree.
111. If every step returns zero the candidates are considered equally good and an ambiguous-overload diagnostic follows.

### Relationship to lookup

112. Lookup does not deduplicate at the `LookupResult` level: a name found along several paths yields several `LookupResultItem`s and collapsing them is `CompareLookupResultItems`' job.
113. `context.bestCandidates` can hold the same declaration more than once, which is why the "no applicable overload" reporting path dedups by rendered signature string before printing notes.

### Partial generic application

114. When the call supplies arguments that pin some but not all of a generic's parameters, the candidate is flagged `IsPartiallyAppliedGeneric` and `CompleteOverloadCandidate` wraps the result in a `PartiallyAppliedGenericExpr`.
115. `TryCheckOverloadCandidateConstraints` short-circuits on that flag, because a later pass of overload resolution supplies the information constraint checking still needs.
116. A `PartiallyAppliedGenericExpr` carries `baseGenericDeclRef` plus `providedOrdinaryArgs`; witness arguments are deliberately not stored on the node and are formed later.
117. Using the partial as the callee of a later invocation hands both to `addOverloadCandidatesForCallToGeneric`, so call-site inference solves the remaining ordinary arguments and all witness arguments together.

### Operator overloading

118. The parser turns `a + b` into an `InvokeExpr` whose `functionExpr` is a `VarExpr` naming the operator.

### The builtin-operator fast path

119. `visitInvokeExpr` tries `convertToLogicOperatorExpr` and then `convertToBuiltinArithmeticOp` before collecting any candidates, and when the latter succeeds the expression is replaced by a fully checked `BuiltinOperatorExpr` and overload resolution never runs for it.
120. `BuiltinOperatorExpr` carries only a `BuiltinOperationKind` and its 1 or 2 operands, with the name-to-kind mapping performed once at creation and the `arity` argument distinguishing prefix `-` (`Neg`) from binary `-` (`Sub`).
121. The recognized set is `+ - * / %`, `== != < > <= >=`, `& \| ^ << >>`, and unary `- ! ~` on builtin integer / floating-point / bool scalars, vectors and matrices.
122. `Conditional`, `And` and `Or` are never produced by the fast path but exist so a resolved call on them can still fold to a compile-time constant, for example `cond ? N : M` in an array size.
123. `getBuiltinArithmeticCommonType` applies the usual arithmetic conversions, so float beats int.
124. Among integers the larger size wins.
125. On an integer size tie the unsigned type wins.
126. `coerceOperandsOfBuiltinBinaryExpr` coerces each operand to its own shape with the common element base, so a `vector * scalar` stays a two-shape operation.
127. The result type is the operand type for arithmetic and bitwise ops, and the same-shape `bool` type for comparisons.
128. The fast path declines the short-circuiting `&&` / `\|\|`, which `convertToLogicOperatorExpr` has already handled.
129. The fast path declines user-defined operand types and mixed shapes that are not broadcast-compatible.
130. The fast path declines mixed-type shift operands, because `a << b` keeps the type of `a` and converts the shift amount independently.
131. In GLSL operator scope only, the fast path declines matrix operands and vector equality; `isGLSLOperatorScope` is true when `-allow-glsl` is set or the `glsl` module is in scope.
132. A bitwise or shift operator with a builtin floating-point operand is diagnosed by the fast path with `Diagnostics::BitwiseOperatorRequiresIntegerOperands`.
133. Unary `~` on a builtin floating-point operand is diagnosed the same way.
134. There is no operator-resolution cache at `source_commit`: `TypeCheckingCache` holds only `conversionCostCache`, which `canCoerce` consults and fills for scalar and vector operand pairs.
135. The `ResolvedOperatorOverload` struct is a declared-but-unreferenced artifact of the removed cache and must not be read as documentation of current behavior.

### The general path

136. Operators the fast path declines reach overload resolution through the same machinery, with the candidate set collected by ordinary lookup of the operator-keyed `Name` in the call site's scope chain.
137. `TryCheckOverloadCandidateFixity` rejects a candidate whose `prefix` / `postfix` modifiers do not match the call form, emitting `Diagnostics::ExpectedPrefixOperator` / `Diagnostics::ExpectedPostfixOperator`.
138. The operand types play no part in finding the candidates: there is no member lookup on the left operand's type and no argument-dependent lookup.
139. A user-declared infix, prefix or postfix operator has to be a free function in scope at the call site; an `operator+` declared inside `struct V` or in an `extension V` is not a name an outside call site can see, and `v1 + v2` there reports no applicable overload.
140. A non-static member form could not match anyway, because the implicit `this` is not one of the call's arguments and arity weighs two operands against a declared parameter list of one.
141. `operator()` is resolved by member lookup on the callee's type when the callee is a value of `DeclRefType`, keeping the implicit `this` through a `Breadcrumb::Kind::This` step that `ConstructLookupResultExpr` replays.
142. `visitIndexExpr` looks `__subscript` up the same way for `a[i]`.
143. A `[mutating]` member operator applied to an immutable base is rejected by `TryCheckOverloadCandidateDirections`, which tests `context.baseExpr->type.isLeftValue`.

### Edge cases and failure modes

144. Two `Applicable` candidates with identical cost, specificity and scope produce `Diagnostics::AmbiguousOverloadForNameWithArgs`, or `AmbiguousOverloadWithArgs` when the callee name is unknown.
145. Each tied candidate is listed as a `Candidate` note, capped at 10 with a trailing `Diagnostics::MoreOverloadCandidates` note for the remainder.
146. When a single non-applicable candidate scores best, the resolver re-runs the pipeline on it in `ForReal` mode so the user sees a per-argument coercion failure rather than a generic "no overload" message.
147. When several non-applicable candidates tie for best, the resolver emits `Diagnostics::NoApplicableOverloadForNameWithArgs` directly, without calling `CompleteOverloadCandidate`.
148. Each candidate note under that error is followed by `Diagnostics::OverloadCandidateArgumentTypeMismatch` — "argument N does not match: expected 'X', got 'Y'".
149. Candidates in that report are sorted by `status` with the declaration's source location as a deterministic tie-breaker, deduped by rendered signature string, and the trailing "N more" count covers unique candidates only.
150. `VariadicPackCountMismatch` maps to `Diagnostics::VariadicPackCountDoesNotMatch`.
151. `GenericArityMismatch` maps to `Diagnostics::GenericSpecializationArityMismatch`.
152. `OrdinaryGenericParamNotInferred` maps to `Diagnostics::GenericParameterCouldNotBeInferred`, naming the parameter that stayed undetermined.
153. `GenericConstraintNotSatisfied` maps to `Diagnostics::GenericArgumentDoesNotSatisfyConstraint` plus a `SeeGenericConstraintDeclaration` note, and is the fallback for every witness-solver constraint kind except interface conformance — equality (`where T == X`), type coercion (`where U(T)`), non-empty pack (`where nonempty(P)`).
154. `GenericParamUnificationConflict` maps to `Diagnostics::GenericParameterUnificationConflict`, reporting both conflicting deductions.
155. `InterfaceConformanceNotSatisfied` maps to `Diagnostics::TypeArgumentDoesNotConformToInterface`.
156. `None` falls back to `Diagnostics::GenericArgumentInferenceFailed`.
157. A pack argument whose length violates a `countof` constraint is solved as part of generic-argument inference, so the mismatch is reported through the `VariadicPackCountMismatch` arm rather than as a separate arity error.
158. A candidate hidden by visibility is silently dropped in `JustTrying` and emits `Diagnostics::DeclIsNotVisible` in `ForReal`; when no candidate applies and some were invisible, the reporting path calls them out with `Diagnostics::InvisibleOverloadCandidate`.
159. Probing applies no per-argument cost ceiling and the accumulated sum has no ceiling either; the candidate is dropped only when `canCoerce` reports that no coercion exists, and `canConvertImplicitly` is never called from `slang-check-overload.cpp`.
160. Scope-distance and overload-rank tie-breaking are skipped when at least one candidate is `Generic` or `UnspecializedGeneric`; cost and specificity still apply, and a remaining tie is reported ambiguous.
161. `float << int` or `~1.0f` are diagnosed as `Diagnostics::BitwiseOperatorRequiresIntegerOperands` by `convertToBuiltinArithmeticOp` rather than surfacing as a "no overload for `operator<<`" message.
162. `[NoDiscard]` is checked after a call has already been resolved, never makes a candidate more or less viable, and contributes no conversion cost.
163. Leaving a `PartiallyAppliedGenericExpr` residual unresolved is a correctness-invariant violation, not a feature.

## Deviation from `_prompt.md`

`_prompt.md` names a target of 15-25 tests, and the manifest's
`size_cap_files` is 70. Following the claim-driven rule that test count is an
output rather than a target, this bundle has 90 tests for 163 enumerated
claims. The overflow is the conversion-cost table: `_claims.md` §2 requires one
test per row of an enumeration the doc spells out, and the table has 40 rows.
Twenty-nine of the 90 tests are `DIAGNOSTIC_TEST` (32 percent), above the
prompt's 30 percent floor.
