# Tests for design/ast-reference/declarations

## Intent

This bundle exercises the user-observable role of each concrete declaration
kind catalogued in
[`docs/generated/design/ast-reference/declarations.md`](../../../../design/ast-reference/declarations.md).
The doc is written as a catalogue of AST classes and their fields, so the
coverage strategy is a translation: for every row of `## Nodes` and every
`## Notable nodes` subsection, the claim under test is the _role_ the doc
assigns to that declaration, and the test is the smallest Slang program whose
behaviour changes if that role were not implemented. Claims about which C++
class the parser allocated, which private field holds what, or which parser
callback ran are recorded under `## Untested claims` rather than probed.

Coverage is organised by declaration family: variables (`VarDecl`, `LetDecl`,
`ParamDecl`, `ModernParamDecl`), aggregates (`StructDecl`, `ClassDecl`,
`EnumDecl`/`EnumCaseDecl`, `InterfaceDecl`, `ExtensionDecl`, the `AggTypeDecl`
link-time alias spelling), aliases (`TypeDefDecl`, `TypeAliasDecl`), callables
(`FuncDecl`, `ConstructorDecl`, `SubscriptDecl`, `FuncExtensionDecl`),
accessors (`PropertyDecl`, `GetterDecl`, `SetterDecl`, `RefAccessorDecl`,
`SemanticDecl`/`SemanticGetterDecl`), generics (`GenericDecl`,
`GenericTypeParamDecl`, `GenericValueParamDecl`, `GenericTypePackParamDecl`,
`GenericValuePackParamDecl`, `AssocTypeDecl`, and all five constraint
spellings the doc enumerates), scoping (`ScopeDecl`, `NamespaceDecl`,
`UsingDecl`, `ImportDecl`), and the misc family (`DeclGroup`, `EmptyDecl` in
its bare-`;`, `__ignored_block` and `__transparent_block` forms, `LambdaDecl`,
`RequireCapabilityDecl`).

Most claims resolve before any backend runs, so `INTERPRET` (value
observation via `printf`) and `DIAGNOSTIC_TEST` (documented rejection) carry
the bundle. The three claims that are genuinely emit-observable — a struct
surviving as an aggregate in target text, and a `ref` accessor's
lowering — fan out across HLSL, GLSL, CUDA, Metal and WGSL, since each backend
spells them differently.

This revision of the source doc turned five previously-unreachable claims into
concrete ones, and each gained a test: the tag type's parsing through the same
inheritance clause a struct uses, the private scope of a hand-written
`__file_decl`, the parse error a statement-bodied property produces, and the
`E38207` a module-scope `type_param` reports when target code is generated from
a use of it without a binding. That takes the bundle to 84 files, four over
the manifest's `size_cap_files: 80`; the overflow is reported here rather than
absorbed by dropping coverage, since each of the five is a distinct documented
diagnostic or surface with no existing test to fold it into.

## Claims

Enumerated per [`_claims.md` §1](../../../_meta/prompts/_claims.md), grouped by
the document's own headings. The page is a catalogue of the compiler's own
`Decl` classes, so the enumeration is split into the statements a compiled
program can reveal and the statements that are properties of the compiler's
headers and parser only; the second group is carried in `## Untested claims`
with reason `internal-source-fact`.

**User-observable**

_`#nodes` (the class table, one claim per user-spellable row)_

1. `DeclGroup` wraps multiple declarations parsed as one group, e.g. `int a, b;`.
2. `VarDecl` is an ordinary mutable variable -- local, global or member -- carrying a type and an initializer expression.
3. `LetDecl` is a `let` variable and is immutable.
4. `ParamDecl` is a function / initializer / subscript parameter, and `ModernParamDecl` is the modern name-first form, immutable unless `out` / `inout`.
5. `ExtensionDecl` is `extension T { ... }` and attaches new members to an existing type.
6. `StructDecl` is a user-defined struct and `ClassDecl` a user-defined class (reference type).
7. `EnumDecl` is the `enum` declaration and each `EnumCaseDecl` child carries a tag expression and value.
8. `InterfaceDecl` is `interface IFoo { ... }` and `InheritanceDecl` is one entry of its `: Base, IFoo` list.
9. `TypeDefDecl` is `typedef X Y;` and `TypeAliasDecl` is the modern `typealias Y = X;`.
10. `AssocTypeDecl` is `associatedtype T` inside an interface.
11. `ScopeDecl` is the anonymous scope the parser creates for block statements, loop headers and lambda parameter lists.
12. `ConstructorDecl` is `__init` or a synthesized constructor, in the UserDefined / SynthesizedDefault / SynthesizedMemberInit flavors.
13. `SubscriptDecl` is `__subscript`, the callable `a[i]` uses.
14. `PropertyDecl` holds `GetterDecl` / `SetterDecl` / `RefAccessorDecl` accessors.
15. `SemanticDecl` declares a `: SV_*`-style semantic and holds typed `SemanticGetterDecl` / `SemanticSetterDecl` accessors.
16. `FuncDecl` is an ordinary function declaration.
17. `FuncExtensionDecl` is the `__func_extension fwd_diff(foo)(...)` shorthand for attaching a custom derivative to an existing function.
18. `NamespaceDecl` is `namespace { ... }` and `ModuleDecl` is the top-level declaration of a translation unit.
19. `UsingDecl` brings a name into scope.
20. `ImportDecl` is `import M;`; `IncludeDecl` is `__include`; `ImplementingDecl` is `implementing M;`; `ModuleDeclarationDecl` is `module M;`.
21. `RequireCapabilityDecl` is `__require_capability`, expressed as a decl so it can be exported.
22. `GenericDecl` is the generic wrapper whose parameter list lives as members and whose genericized declaration is `inner`.
23. `GenericTypeParamDecl`, `GenericValueParamDecl`, `GenericTypePackParamDecl` (`each T`) and `GenericValuePackParamDecl` (`let each N`) are the four generic parameter forms.
24. `GenericTypeConstraintDecl` is a `T : U` or `T == U` constraint, `TypeCoercionConstraintDecl` a `where To(From)`, `NonEmptyPackConstraintDecl` a `where nonempty(Pack)`, `GenericVariadicPackCountConstraintDecl` a `where countof(Pack) == N`, and `HasDiffTypeInfoConstraintDecl` a `where __hasDiffTypeInfo(T)`.
25. `EmptyDecl` is an empty declaration that exists only to carry modifiers, and is also what `__ignored_block` / `__transparent_block` produce.
26. `GlobalGenericParamDecl` (`type_param`) and `GlobalGenericValueParamDecl` (`__generic_value_param`) are module-level parameters bound by an external specialization argument.
27. `AttributeDecl` binds the spelling `[name(args)]` to an AST attribute class the compiler already knows; its body is the parameter list.

_`#genericdecl`_

28. The parser parses the parameter list as members of the `GenericDecl` itself and puts the genericized declaration in `inner`, so the rest of the front end can treat a generic as "the inner decl with a parameter list".
29. `InterfaceDefaultImplDecl` is what the parser builds for an interface member written with a body: the member is re-parsed inside a fresh generic whose single parameter is `This` constrained to the enclosing interface, renamed `<name>$defaultImpl`, and the original requirement marked with `HasInterfaceDefaultImplModifier`.

_`#extensiondecl` / `#funcextensiondecl`_

30. An extension's target is resolved by name lookup during checking, which is why it is stored as a `TypeExp` rather than a resolved type at parse time.
31. `__func_extension` attaches a custom forward derivative, backward derivative or `__apply` to an existing function without modifying its definition, and is desugared into an `ExtensionDecl` so the rest of the pipeline never sees the shorthand.

_`#aggtypedecl-structdecl-classdecl-enumdecl`_

32. `StructDecl` is the value-type variant and `ClassDecl` the reference-type one; all three aggregate forms share container behaviour.
33. `AggTypeDecl::aliasedType` holds the right-hand side of the link-time alias spelling `struct FooAlias : IFoo = Foo;`.

_`#inheritancedecl`_

34. After checking, an inheritance clause's `witnessTable` records how the containing type satisfies each requirement of the base interface.

_`#syntaxdecl-and-the-syntax-as-declaration-model`_

35. `attribute_syntax` binds a spelling rather than defining one: the `: <class>` clause must name an AST node class the compiler was built with, the parser runs no attribute-specific logic, and the attribute's checking -- including which declarations it may be placed on -- comes from that C++ class.
36. A user module can therefore add a new *spelling* for an existing attribute class, but not a genuinely new attribute; all 126 `attribute_syntax` declarations in the tree ship with the compiler.

_`#namespacedecl-moduledecl-filedecl`_

37. Multiple textual namespace declarations with the same name in one module are collapsed into one `NamespaceDecl` during parsing.
38. `FileDecl`'s transparency belongs to the file scopes the compiler builds, not to the node: `parseFileDecl` gives a hand-written `__file_decl { ... }` the same private scope any other container gets, so its members are not visible to the rest of the file.
39. The `FileDecl` an `__include` or `implementing` produces is the one whose scope gets spliced into the module's lookup chain.
40. `ModuleDecl::languageVersion` and `defaultVisibility` decide the default visibility of everything inside the module.

_`#enumdecl-and-enumcasedecl`_

41. An `EnumDecl` is an `AggTypeDecl` so enum types can have conformances and member functions like any other type, while `EnumCaseDecl` is a regular `Decl`.
42. The tag type is written where a base list would go -- `enum E : uint8_t { A, B }` -- and `parseEnumDecl` calls the same `parseOptionalInheritanceClause` a struct uses, so the tag type and any interface conformances arrive side by side.
43. `EnumDecl::tagType` is never set by the parser; checking picks the tag type out of that inheritance list.

_`#accessordecl-family`_

44. The parser only creates an accessor when an explicit `get` / `set` / `ref` keyword is present, so a body made of statements -- `property int p { return v; }` -- is a parse error rather than an implicit getter.
45. The empty body `{ }` and the semicolon form `property int p;` both leave the declaration with no accessor member, which is the case treated like `{ get; }` and later materialized as an implicit `GetterDecl`; that is what makes `property int p { }` a well-formed get-only interface requirement.
46. Each accessor's body is parsed lazily, like any other function body.

_`#semanticdecl`_

47. A `semantic` declaration introduces a name usable in the `: Name` position of a field or parameter, and its accessors carry a type instead of a body: only `get : <type>;` and `set : <type>;` are accepted inside the braced body.

_`#requirementdecl-style-nodes-inside-interfacedecl` / `#assoctypedecl`_

48. An interface requirement is whatever `Decl` was written inside the interface body; there is no separate requirement class.
49. When an associated type sits directly inside an interface, its constraint is redirected to that interface so it becomes a sibling rather than a child, which is why `associatedtype A : IBar` and `associatedtype A where A : IBar` produce identical ASTs.

_`#generictypeconstraintdecl-as-an-interface-requirement`_

50. `where T : IBar` allows a comma-separated list of supertypes, producing one decl per supertype, and `where T == U` sets the equality flag.
51. The reversed spelling `N == countof(Pack)` is recognized only in order to report that the count must be on the left.
52. In `where To(From)`, `toType` is the type before the parentheses and `fromType` the one inside, and a trailing `implicit` keyword attaches an implicit-conversion modifier.
53. Every spelling except `__hasDiffTypeInfo` also accepts a leading `optional`.
54. `__constraint <type> : <type>;` inside an interface, an inheritance-style bound on an associated type, and a `where`-clause bound on an associated type all collapse to the same representation.

_`#globalgenericparamdecl-and-globalgenericvalueparamdecl`_

55. `type_param T;` and `__generic_value_param N : int;` are module-scope declarations that take no argument where they are written; each becomes a specialization parameter of the enclosing module.
56. Compiling the module on its own succeeds even when the parameter is used, and so does a target compile of a file that declares one and never uses it.
57. Generating target code from a *use* without a binding reports `error[E38207]: global generic parameter used in code without a concrete binding`, located at the declaration.
58. The command-line `-specialize` option does not supply the binding -- it feeds the last entry point rather than the module -- so using it for a module-level parameter reports `error[E38025]: wrong number of specialization arguments`.

**Internal-source facts** (no user-observable consequence; carried in `## Untested claims`)

60. The `Key fields` column of the node table.
61. The parser entry points the page names (`ParseDecl`, `parseExtensionDecl`, `parseAssocType`, `parseOptionalGenericConstraints`, `maybeParseGenericConstraints`, `parseInterfaceConstraintDecl`, `parseSemanticAccessorDecl`, `isDeclAllowed`, and the `isConstraintDecl` / `isGenericConstraintParameterDecl` split).
62. `SyntaxDecl` binds a keyword to a parser callback, one per `g_parseSyntaxEntries` entry created by `populateBaseLanguageModule`.
63. The synthesized-only classes: `SynthesizedStructDecl`, `SynthesizedFuncDecl`, `InterfaceDefaultImplDecl`, `ThisTypeDecl`, `ThisTypeConstraintDecl`, `FuncAliasDecl`, `LambdaDecl`, `FuncConstraintDecl`.
64. `GLSLInterfaceBlockDecl` has a parse function of its own that nothing calls, so no source spelling produces the node; the GLSL block spellings desugar to a `StructDecl` plus a `VarDecl` instead.
65. `UnresolvedDecl` is declared with no state and nothing constructs one, so its intended role cannot be established from the watched paths.
