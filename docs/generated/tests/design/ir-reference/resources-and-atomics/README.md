# Tests for design/ir-reference/resources-and-atomics

## Intent

This bundle exercises the per-opcode catalog in
[`docs/generated/design/ir-reference/resources-and-atomics.md`](../../../../design/ir-reference/resources-and-atomics.md):
the IR opcodes that operate on GPU resources (structured, byte-address,
append/consume buffers; textures and images; descriptor heaps;
cooperative matrix and vector; mesh outputs; raytracing payloads) and
the thirteen members of the `AtomicOperation` group.

The catalog rows make one testable kind of claim — _surface construct X
produces IR opcode Y with operand shape Z_ — so the dominant strategy is
`//TEST:SIMPLE(filecheck=IR):-target spirv-asm -dump-ir -o /dev/null
-stage compute -entry main`, with CHECK patterns anchored at
`func %main` when the opcode belongs to the user body, and matched
globally when the opcode is created inside a core-module function body
that the dump pulls in (`byteAddressBufferLoad`, `byteAddressBufferStore`,
`imageGatherOffset`, `StructuredBufferGetDimensions`). Operands are
derived from `SV_DispatchThreadID` wherever a literal would let the
constant folder collapse the instruction away.

Three groups of claims are not opcode-shape claims and get a different
observation point. Opcodes synthesized by target legalization
(`getOptiXPayloadRegister`, `GetVulkanRayTracingPayloadLocation`,
`ImageTexelPointer`) sit _after_ the `-dump-ir` snapshot, so those tests
pin the backend text instead. Claims about opcodes that a surface does
_not_ produce (`Interlocked*`, `GroupMemoryBarrierWithGroupSync`,
`WaveGetActiveMask`) pin the call form in IR and then the per-target
emitted text, which is what the "wrapper, not an opcode" and "no
producer" notes assert. Finally, `getNaturalStride` and
`getNaturalAlignment` fold to literals before emit, so their values are
verified functionally with `COMPARE_COMPUTE -cpu` and re-checked across
every text-emit target.

Boundary coverage follows the buffer-index and integer axes the catalog
implies: element index `0`, `INT_MAX`, a negative literal, and an
unsigned index for each buffer family; `0`, `INT_MIN`, `INT_MAX`,
`UINT_MAX`, an all-zero mask, and an all-ones mask for the atomic value
operand; and every non-relaxed `IRMemoryOrder` enumerator for the
undeclared trailing order operand.

A fourth group is the prose the source doc's gap-intake pass made concrete:
the underscore-prefixed resource queries that reach the lowering snapshot
with no wrapper to inline through, the `GetAttributeAtVertex` surface that
picks between `ResolveVaryingInputRef` and `GetPerVertexInputArray` by
target, the `beginInvocationInterlock()` / `endInvocationInterlock()`
spellings and their `fragment`-stage requirement, the OptiX SBT worked
example plus its two carve-outs, and the `-capability spvDescriptorHeapEXT`
arm of `DescriptorHandle<T>`. Those claims name exact emitted text, exact
opcode spellings, and `E36107` rejections, so each is pinned to what the
compiler was observed to produce.

### Texture and image

1. `imageSubscript(image, coord, sampleCoord?)` is a pointer-like value for one texel, produced from the `_Texture` subscript `__ref` accessors so `image[coord]` can appear as an lvalue, and is legalized away before emit.
2. `imageLoad(image, coord, auxCoord1?, auxCoord2?)` loads a texel, where `auxCoord1` is the sample coord on GLSL/SPIR-V and the array-or-sample coord on Metal and `auxCoord2` is the Metal sample coord.
3. `imageStore(image, coord, value)` stores a texel and may carry up to two further, undeclared aux coords.
4. `imageGatherOffset(sampledImage, location, component, offset)` gathers the same `component` of the four texels surrounding `location`, displaced by a whole-texel `offset`.
5. `ImageTexelPointer(image, coord, sample)` forms a pointer to a texel so an atomic can target it, and emits as `OpImageTexelPointer`.
6. `SubpassLoad(subpassInput, sample?)` reads a fragment-shader input attachment, the optional operand selecting an MSAA sample.
7. `MetalCastToDepthTexture(texture)` reinterprets a texture as a Metal depth texture.
8. `IsTextureAccess`, `IsTextureScalarAccess`, and `IsTextureArrayAccess` are declared but have no producer at HEAD.
9. `ExtractTextureFromTextureAccess`, `ExtractCoordFromTextureAccess`, and `ExtractArrayCoordFromTextureAccess` have core-module declarations only and are never called.

### Sampling and combined samplers

10. `sample(texture, sampler, coord)` and `sampleGrad(texture, sampler, coord, gradX)` have full generated wrappers but no code creates or consumes them at HEAD.
11. `makeCombinedTextureSampler(texture, sampler)` pairs a separate texture and sampler into one combined value.
12. `MakeCombinedTextureSamplerFromHandle(handle)` builds a combined texture/sampler from a descriptor handle.
13. `CombinedTextureSamplerGetTexture(sampler)` and `CombinedTextureSamplerGetSampler(sampler)` project the two halves, and both are consumed and removed by the combined-texture-sampler lowering pass.

### Buffer load and store

14. `ByteAddressBuffer.Load(offset)` produces `byteAddressBufferLoad(buffer, offset, alignment)`, loading ordinary data of the result type at `offset` bytes.
15. `byteAddressBufferStore(buffer, offset, alignment, value)` stores ordinary data at `offset` bytes.
16. `sBuf.Load(index)` on a read-only `StructuredBuffer` produces `structuredBufferLoad([buffer], [index])`.
17. `structuredBufferLoadStatus(buffer, index, status)` is a load that also writes a residency-status output.
18. `rwBuf.Load(index)` produces `rwstructuredBufferLoad([buffer], [index])`, loading from a writable structured buffer.
19. `rwstructuredBufferLoadStatus([buffer], [index], [status])` is a load with status from a writable structured buffer.
20. `rwstructuredBufferStore(structuredBuffer, index, val)` has no core-module origin — it is synthesized when a store through a buffer pointer is legalized back into a buffer operation.
21. `rwstructuredBufferGetElementPtr(base, index)` is a pointer to the `index`-th element.
22. `sBuf.GetDimensions(count, stride)` produces `StructuredBufferGetDimensions(buffer)`, returning element count and stride.

### Append and consume buffers

23. `AppendStructuredBuffer.Append(v)` produces `StructuredBufferAppend(buffer, element?)`; the `element` operand is declared optional but every producer supplies it and the emitters read `getOperand(1)` unconditionally.
24. `ConsumeStructuredBuffer.Consume()` produces `StructuredBufferConsume(buffer)`, popping one element.

### Resource queries and modifiers

25. `NonUniformResourceIndex(i)` produces `nonUniformResourceIndex(index)`, marking a resource index as divergent.
26. `getNaturalStride(type)` is the byte stride of the operand's natural layout and is folded to a literal by peephole.
27. `getNaturalAlignment(type)` is the power-of-two alignment guaranteed by that layout.
28. `castDynamicResource(resource)` narrows a `__DynamicResource` to a concrete resource type.
29. `getEquivalentStructuredBuffer([buffer])` views a byte-address buffer as a structured buffer and is consumed and removed by byte-address legalization.
30. `getStructuredBufferPtr([buffer])` is a `T*` pointer to a structured buffer's data.
31. `getUntypedBufferPtr([buffer])` is a `uint*` pointer to a byte-address buffer's data.
32. `getRegisterIndex([resource])` is the register index the resource is bound to, and is a child of the `BindingQuery` group.
33. `getRegisterSpace([resource])` is the register space the resource is bound to, and is a child of the same group.
34. Five of these rows have no public wrapper — the underscore-prefixed declarations are the whole surface — so unlike `InterlockedAdd` or `WaveGetActiveMask` they *do* appear at the lowering snapshot, with no inlining step in between.

### Shader IO

35. A module-scope `VarDecl` lowers through `lowerGlobalShaderParam` to a `global_param`, which carries the global op flag.
36. `GetWorkGroupSize` is nullary and hoistable, so `materializeGetWorkGroupSize` replaces it once the referencing entry point is known.
37. `GetCurrentStage` is the pipeline stage of the calling entry point and is folded away by stage-switch specialization.
38. `GetPerVertexInputArray([attribute])` is an array view of a `nointerpolation` input across the primitive's vertices.
39. `ResolveVaryingInputRef([attribute])` is a placeholder reference to a varying input, rewritten to the real parameter by varying-param legalization.
40. The last two rows share one user surface: `GetAttributeAtVertex(attribute, vertexIndex)`, called from a `fragment` entry point on an input declared `nointerpolation`.
41. Which of the two opcodes you get is a target decision, not a source one: the `__target_switch` produces `ResolveVaryingInputRef` on its own for `hlsl`, and wraps that reference in `GetPerVertexInputArray` before subscripting it for `glsl` / `spirv`.
42. The `fragment` requirement is enforced by capability checking — the same call in a `vertex` entry point is rejected with `E36107`.

### Mesh-shader outputs

43. `meshOutputRef(base, index)` is a reference to one slot of a mesh output array.
44. `meshOutputSet(base, index, elementValue)` writes one element of a mesh output array.
45. `metalSetVertex(index, elementValue)` is the Metal `_slang_mesh.set_vertex` write.
46. `metalSetPrimitive` and `metalSetIndices` have no producer at HEAD — they are consumed by the Metal emitter but never emitted.

### Atomic operations

47. All thirteen atomics are children of the Lua `AtomicOperation` group, and operand 0 is always the destination pointer, which is the only thing `validateAtomicOperations` checks.
48. The memory-order operand is real but undeclared: the Lua `operands` lists stop at the value operands, so no accessor is generated and the backends read it positionally.
49. The ordering value is `IRMemoryOrder`: `Relaxed = 0`, `Acquire = 1`, `Release = 2`, `AcquireRelease = 3`, `SeqCst = 4`.
50. The Slang-level spelling a user writes is the `MemoryOrder` enum whose enumerators are `Relaxed`, `Acquire`, `Release`, `AcquireRelease` and `SeqCst`, each defined by a `$(kIRMemoryOrder_*)` splice of the C++ constant so the two cannot drift.
51. There is no memory-*scope* operand; the SPIR-V backend hard-codes `SpvScopeDevice` in every atomic case.
52. Each atomic has two producer surfaces, both declared with the same `__intrinsic_op`: the free `__atomic_*<T>` intrinsics and the `Atomic<T>` methods.
53. `load`, `store`, `exchange` and `compareExchange` are available for every `IAtomicable` `T`; `add`/`sub`/`max`/`min` require `IArithmeticAtomicable`; `and`/`or`/`xor`/`increment`/`decrement` require `IBitAtomicable`, which is why `Atomic<float>.and(v)` is rejected as a missing member rather than as a bad argument type.
54. `Atomic<T>.load` produces `atomicLoad([ptr], [order])`, atomically reading `*ptr`.
55. `Atomic<T>.store` produces `atomicStore([ptr], [val], [order])`, atomically writing `*ptr`.
56. `Atomic<T>.exchange` produces `atomicExchange`, which writes and returns the previous value.
57. `Atomic<T>.compareExchange` produces `atomicCompareExchange(ptr, expected, desired, [successOrder], [failOrder])`.
58. `Atomic<T>.add` produces `atomicAdd(ptr, val, [order])`, returning the old value.
59. `Atomic<T>.sub` produces `atomicSub(ptr, val, [order])`.
60. `Atomic<T>.and` produces `atomicAnd(ptr, val, [order])`.
61. `Atomic<T>.or` produces `atomicOr(ptr, val, [order])`.
62. `Atomic<T>.xor` produces `atomicXor(ptr, val, [order])`.
63. `Atomic<T>.min` produces `atomicMin(ptr, val, [order])`.
64. `Atomic<T>.max` produces `atomicMax(ptr, val, [order])`.
65. `Atomic<T>.increment` produces `atomicInc(ptr, [order])`, which emits `OpAtomicIIncrement` on SPIR-V.
66. `Atomic<T>.decrement` produces `atomicDec(ptr, [order])`.
67. `MetalAtomicCast([value])` reinterprets a value as Metal's `atomic<T>` but has no producer at HEAD.
68. The `atomic_reduce` family and the `Atomic<T>.reduce*` methods add no opcodes: each is a `[ForceInline]` `__target_switch` that emits inline CUDA `red.*` assembly for CUDA and otherwise falls through to the matching `__atomic_*` intrinsic, so the IR ends up with an ordinary `atomicAdd` whose result is unused.
69. `IncrementCoverageCounter` carries no operands — its position is the per-instruction `sourceLoc`, which `stripDebugInfo` never removes — and the coverage pass rewrites it into an atomic add on the synthesized `__slang_coverage` buffer.
70. `IncrementFunctionCoverageCounter` carries `functionName` and `functionMangledName` as `IRStringLit` operands so later passes need no AST access.
71. `IncrementBranchCoverageCounter` carries `branchSiteID`, `branchArmID` and `branchArmKind` as `IRIntLit` operands, the arm kind letting LCOV export distinguish true/false/case arms.

### Barriers and synchronization

72. `ControlBarrier` is nullary, synthesized when GLSL legalization needs a sync point, and emitted as `barrier()` / `OpControlBarrier`.
73. `GroupMemoryBarrierWithGroupSync` has no producer at HEAD.
74. `BeginFragmentShaderInterlock` opens a rasterizer-ordered critical section and `EndFragmentShaderInterlock` closes it.
75. The Slang a user writes to reach those two is `beginInvocationInterlock()` and `endInvocationInterlock()`, and they require a `fragment` entry point because the rasterizer ordering they request has no meaning in another stage.
76. `ControlBarrier` has no direct spelling at all; it is synthesized by GLSL legalization.
77. The HLSL barrier family a user does call — `AllMemoryBarrier`, `GroupMemoryBarrier`, `DeviceMemoryBarrier`, each also in a `WithGroupSync` form, plus the `WithWaveMaskSync` variants — does not lower to these opcodes.
78. The general-purpose `Barrier(memoryType, semantics)` intrinsic is not on this page: its flag arguments are carried by the `getEnumBarrierMemoryTypeFlags` / `getEnumBarrierSemanticFlags` opcodes documented in `misc.md`.

### Cooperative matrix and vector

79. `CoopMatMapElementIFunc` applies an `IFunc` element-wise over a cooperative matrix.
80. `CoopMatMulAdd(matA, matB, matC, saturatingAccumulation)` is a fused multiply-add on cooperative matrices.
81. `CoopVecMatMulAdd` is a cooperative-vector matrix-multiply-add with an optional bias in its trailing three operands.
82. `CoopVecOuterProductAccumulate` accumulates the outer product of `a` and `b` into a matrix in memory.
83. `CoopVecReduceSumAccumulate(bufferPtr, offset, value)` accumulates a reduce-sum into a memory location.

### Wave intrinsics

84. Only the three *mask* opcodes live on this page; the rest of the wave intrinsics stay as core-module calls until backend emit.
85. `waveGetActiveMask` is nullary and yields the mask of currently active lanes.
86. `waveMaskBallot(mask, condition)` is threaded through control flow by the active-mask synthesis pass for CUDA.
87. `waveMaskMatch(mask, value)` comes from the same pass and yields the mask of lanes sharing the same `value`.

### Raytracing payload

88. `getOptiXRayPayloadPtr` is a nullary hoistable pointer to the OptiX payload struct reassembled from payload registers.
89. `getOptiXHitAttribute([type], [index])` reads one hit attribute, taking the *type* inst as operand 0 and the attribute index as operand 1.
90. `getOptiXSbtDataPointer` is nullary and its enumerator is `kIROp_GetOptiXSbtDataPtr`.
91. `getOptiXPayloadRegister([registerIndex])` reads one 32-bit OptiX payload register.
92. `setOptiXPayloadRegister([registerIndex], [value])` writes one 32-bit OptiX payload register.
93. `GetVulkanRayTracingPayloadLocation([payload])` is the location index assigned to a Vulkan raytracing / callable payload.
94. What produces `getOptiXSbtDataPointer` is *where* a uniform is declared, not how large it is: only an entry-point `uniform` **parameter**, on a stage other than compute, is collected into the SBT record, one scalar is enough, the opcode is typed `ConstantBuffer(%ShaderRecordParams, DefaultLayout)`, and the emitted CUDA reads `((ShaderRecordParams_0*)optixGetSbtDataPointer())->scale_0`.
95. A module-scope `uniform` global instead becomes an ordinary `global_param` read out of the CUDA global parameter block.
96. A `compute` entry point is skipped by the pass — its `uniform` parameter becomes a kernel launch argument.

### Descriptor heaps

97. `LoadResourceDescriptorFromHeap(index)` loads a resource descriptor by heap index.
98. `LoadSamplerDescriptorFromHeap(index)` loads a sampler descriptor by heap index.
99. `SPIRVLoadDescriptorFromHeap(heap, index)` loads a descriptor out of an explicit SPIR-V heap array.
100. `SPIRVLoadTexelPointerFromHeap(heap, index, textureType, coord, sampleIndex)` forms a texel pointer directly from a heap descriptor so an atomic can target a bindless image.
101. `SPIRVResourceHeap` is the nullary hoistable stand-in for the implicit SPIR-V resource-descriptor array.
102. `SPIRVSamplerHeap` is the nullary hoistable stand-in for the implicit SPIR-V sampler-descriptor array.
103. The surface behind every descriptor-heap row is `DescriptorHandle<T>`, each dereference of which goes through `defaultGetDescriptorFromHandle`, whose `__target_switch` chooses the heap form.
104. Compiled with `-capability spvDescriptorHeapEXT` the two heap opcodes are *core-module* intrinsics that are in the IR from linking onward, and the emitted binary names `slang_resourceHeap` / `slang_samplerHeap` and requests `SPV_EXT_descriptor_heap`.
105. Without that capability the same shader falls to the plain `spirv` case, uses `GetDynamicResourceHeap`, and emits `__slang_resource_heap`.
106. SPIR-V legalization is the second producer, reached only from the combined-texture-sampler arm; `SPIRVLoadTexelPointerFromHeap` has no other producer at all, and neither is visible under `-dump-ir`.

### Notable opcodes

107. `imageSubscript` is not the load itself — it models a *pointer to a texel*, which is what makes `image[coord] = v` and `image[coord] += v` type as lvalues.
108. The image-subscript legalization pass rewrites each `imageSubscript` into explicit `imageLoad` / `imageStore` pairs for a read-modify-write, so `imageLoad` has no core-module origin at all.
109. The fourth argument of the core module's `__metalImageStoreArray` lands in `imageStore`'s operand 3 — an operand the Lua never mentions — and the Metal backend then emits `tex.write(value, coord, auxCoord1)`.
110. `imageGatherOffset`'s `offset` may be either a compile-time constant or a runtime value, and the backends distinguish the two cases.
111. Texture sampling reaches the backends as ordinary core-module calls with a `TargetIntrinsicDecoration`, not through the `sample` / `sampleGrad` opcodes, so a `sample` in an IR dump is a signal that something unexpected happened.
112. The three `Extract*FromTextureAccess` opcodes can only appear if user code names the underscore-prefixed intrinsic directly, and no backend consumes any of the six texture-access helpers.
113. `byteAddressBufferStore`'s real operand order is `buffer, offset, alignment, value`; the builder's three-argument overload inserts a literal `0` alignment at index 2 and the HLSL emitter writes `.Store(getOperand(1), getOperand(count - 1))`.
114. Because the FIDDLE accessors are generated straight from the Lua names, `IRByteAddressBufferStore::getValue()` returns the **alignment** and `getAlignment()` returns the **value**, so callers must use `getOperand(2)` and `getOperand(3)`.
115. `rwstructuredBufferGetElementPtr` is the lvalue counterpart of `rwstructuredBufferLoad`, returning a pointer so ordinary `Store`, `FieldAddress` and `GetElementPtr` opcodes can be chained onto it, and the `__ref` subscript accessor is what makes `buf[i].field = v` work.
116. Because the `MemoryOrder` default is materialized at the call site during checking, the order operand is always present in the lowered IR.
117. Backends index it positionally: `atomicLoad`, `atomicInc` and `atomicDec` put the order at operand 1; `atomicStore`, `atomicExchange` and the seven read-modify-write atomics put it at operand 2; `atomicCompareExchange` puts the success order at operand 3 and the failure order at operand 4.
118. `atomicCompareExchange` is the only atomic with two memory orders.
119. The core module documents two constraints the IR does not enforce: `successOrder` must be at least as strong as `failOrder`, and `failOrder` may not be `Release` or `AcquireRelease`.
120. The result of `atomicCompareExchange` is the value that was previously stored, so callers compare it against `expected` to learn whether the swap happened.
121. `InterlockedAdd` and its siblings are not `__intrinsic_op` declarations but `[ForceInline]` Slang functions whose bodies call the corresponding `__atomic_*` intrinsic, so immediately after AST lowering you see `call %InterlockedAdd(...)`, not `atomicAdd`.
122. `Atomic<T>` is the surface that lowers straight to the opcode — `counter.add(1)` becomes an `atomicAdd` with no intervening call.
123. One `atomicAdd` in the IR corresponds to one *statement*, not one thread; contention across a dispatch is implicit in the launch and the IR carries no fan-out.
124. The same wrapper pattern hides `waveGetActiveMask`, `imageSubscript`, `StructuredBufferGetDimensions`, and the `atomic_reduce` `atomicAdd` from a search of `func %main` in a fresh `-dump-ir`.
125. An `AST origin` cell naming an `__intrinsic_op` line tells you where the opcode is *declared*, not the earliest IR in which you can observe it.
126. `getNaturalStride` and `getNaturalAlignment` take a *value*, not a type inst — the `[__unsafeForceInlineEarly]` wrappers pass `__declVal<T>()` — and the opcode inspects the operand's type.
127. `float4` gives alignment 16, `float2` and `half4` give 8, and `float3` gives 4 because its 12-byte stride is not a power of two.
128. Both are folded to literals by peephole and neither survives to emit.
129. `nonUniformResourceIndex` is a value-level identity — result and operand share a type — that exists purely to carry the information that the index diverges across lanes, so SPIR-V attaches a `NonUniform` decoration and HLSL re-emits the intrinsic.
130. It has three declaration sites because HLSL permits it on non-integer types too.
131. `LoadResourceDescriptorFromHeap`'s single operand is the heap index while the *result type* carries the resource type, which is how the backend knows which descriptor cast to emit; on D3D12 that is enough because the heap is implicit.
132. Entry-point provenance is not a separate opcode: it is an `EntryPointParamDecoration` attached to the `global_param`, and the layout opcodes attach as children that backend emit walks to recover the binding.
133. `GroupMemoryBarrierWithGroupSync` has no producer because the core-module function of the same name is implemented with `__intrinsic_asm` per target, not `__intrinsic_op`, so calling it never creates the opcode.
134. The `IRBuilder::emitMetalSetPrimitive` and `emitMetalSetIndices` helpers are defined but never called, and both pass `kIROp_MetalSetVertex` to `createInst`, so they would produce the wrong instruction if they were called.
135. `IROpInfo::fixedArgCount` is documented as the required-argument count but is computed as `#value.operands`, so the table records 3 for `imageSubscript` and 2 for `StructuredBufferAppend` even though those are legal with 2 and 1 operands; the field is not read anywhere in the compiler.

### Internal-source facts

136. Every opcode on the page is declared in `slang-ir-insts.lua`, spread across the fifteen line regions the `## Source` table lists.
137. Most opcodes have no dedicated `visit*` method in `slang-lower-to-ir.cpp`: they originate from `__intrinsic_op` declarations in the core module, which lowering turns into the named opcode through `emitIntrinsicInst`.
138. Every opcode in the family has an `IRFoo` C++ wrapper; hand-written structs are spelled out in `slang-ir-insts.h` with a `FIDDLE()` / `FIDDLE(leafInst())` pair, generated ones are emitted into the fiddle header.
139. Named operand accessors are generated for **both** kinds from the Lua `operands` list.
140. A generated struct gets a null-returning guard for an optional operand while a hand-written struct gets the unguarded form, which is why `IRImageSubscript` and `IRImageLoad` hand-write `hasSampleCoord()` / `hasAuxCoord1()` / `hasAuxCoord2()` predicates.
141. The generated enumerator is `kIROp_` + the entry's `struct_name`, which is *not* always the Lua key — `global_param` → `kIROp_GlobalParam`, `getOptiXSbtDataPointer` → `kIROp_GetOptiXSbtDataPtr`, and the lowercase mnemonics whose `struct_name` is capitalized.
142. The operand column's notation — plain name, trailing `?`, square brackets, em-dash — encodes whether a named accessor is generated.
143. `AtomicOperation` and `BindingQuery` are the only Lua *grouping* parents on this page, and neither has its own `kIROp_` enumerator: they generate `kIROp_First…` / `kIROp_Last…` range bounds instead.
