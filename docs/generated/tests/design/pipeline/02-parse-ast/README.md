# Tests for design/pipeline/02-parse-ast

## Intent

This bundle exercises the parsing stage described in
[`docs/generated/design/pipeline/02-parse-ast.md`](../../../../design/pipeline/02-parse-ast.md):
how a flat post-preprocess token list becomes a strongly-typed AST. The
claims decomposed into tests come from the doc's own sub-sections —
two-stage parsing (decl-stage capture of `UnparsedStmt` and the
body-stage re-parse), syntax-as-declaration (keywords bound to parse
callbacks through the `SyntaxParseInfo` table rather than reserved by the
lexer), error recovery (the recovering flag, `TryRecover`'s
recover-before / recover-after sets, and balanced-group skipping), the
five user-observable AST node families, `ASTBuilder` type interning, the
`<` disambiguation strategy and every generic-constraint spelling the
doc enumerates, interface associated-type / `__constraint` requirements,
modifier and attribute parsing, and the parse-time diagnostics listed
under `## Failure modes` (keyword-used-as-name, operator-name-on-a-
non-function, and the floating-point literal classification and range
reports).

Coverage strategy: one test per claim, plus extra probes on the axes the
doc itself commits to — every constraint spelling, every declaration
kind the shared declarator path covers, and the three float-literal
range/precision edges. Parser claims are target-independent, so the
functional tests use `//TEST:INTERPRET` rather than a per-target emission
fan-out; the one matrix probe uses CPU `COMPARE_COMPUTE` because the
interpreter has no matrix precedent in the suite. Rejection claims use
`//DIAGNOSTIC_TEST:SIMPLE` in exhaustive mode, so "exactly this
diagnostic and no other" is part of the assertion — that is what makes
the cascade-suppression and not-flagged-twice claims testable at all.
Lex-surface and keyword-inventory claims stay in
`design/pipeline/01-lex-preprocess` and
`design/syntax-reference/keywords-and-builtins`; every test here fails
because of something the parser (or the checking pass the doc explicitly
hands off to) did.

**`## Inputs and outputs`**

1. `parseSourceFile` takes an `ASTBuilder`, a `TranslationUnitRequest`, a `SourceLanguage`, a `TokenSpan`, a `DiagnosticSink`, an outer `Scope*`, and a `ContainerDecl*` parent.
2. The output is AST nodes attached to `parentDecl`, allocated through the `ASTBuilder` passed in.
3. Function and method bodies are still unparsed when this stage finishes.

**`## Parser`**

4. The parser is recursive-descent and can use arbitrary lookahead over the pre-collected flat token list, although it rarely looks ahead more than one token.
5. The token stream is consumed through `TokenReader`, which exposes `peekToken`, `peekTokenType`, `peekLoc`, `advanceToken`, plus `ParsingCursor` save / restore for backtracking.

**`### Two-stage parsing`**

6. At the decl-parse stage the parser does not recurse into a `{ ... }` function body; `parseOptBody` tracks brace nesting and copies the enclosed tokens into an `UnparsedStmt`.
7. The `UnparsedStmt` also records the scopes the body was written in (`currentScope`, `outerScope`).
8. At the body-parse stage, semantic checking spawns a new `Parser` in body mode and re-parses those tokens with a back-pointer to the `SemanticsVisitor`.
9. `parseSourceFile` selects `ParsingStage::Decl` and `parseUnparsedStmt` selects `ParsingStage::Body`; code that must differ consults `Parser::getStage()`.
10. The two-stage scheme exists primarily to disambiguate `<` between a generic argument list and a less-than comparison.
11. At body-parse time `tryParseGenericApp` can hand the expression before the `<` to the checker's `CheckTerm` and act on what it names.
12. A base that resolves to a `GenericDecl`, to a `FunctionDeclBase`, or to an `AggTypeDeclBase` all commit to the generic reading, and an overloaded base commits if any candidate is one of those three.
13. Only a base that resolves to something else — an ordinary variable, say — forces the comparison reading.

**`### Syntax-as-declaration`**

14. Slang treats most keywords not as lexer-level reserved words but as identifiers bound to syntax in the active environment.
15. The parser keeps a `SyntaxParseInfo` table mapping keyword names to parse callbacks, handed out by `getSyntaxParseInfos()`.
16. The table is the static array `g_parseSyntaxEntries[]`, whose rows are built by `_makeParseDecl`, `_makeParseModifier`, and `_makeParseExpr`.
17. When the parser sees an identifier it looks it up in the active scope chain with `tryLookUpSyntaxDecl`, and `tryParseUsingSyntaxDecl` invokes the callback of any `SyntaxDecl` the lookup yields.
18. That lookup is the first thing `ParseDeclWithModifiers` tries for an identifier-initial declaration, and the same mechanism dispatches modifier keywords from `ParseModifiers`.
19. Most language modifier keywords are populated at startup by `populateBaseLanguageModule`, and the core module's `*.meta.slang` files contribute additional entries.
20. Adding a new modifier keyword is typically a matter of registering it in the syntax table, not of touching the lexer or parser core.

**`### Angle-bracket annotations`**

21. Two independent places discard a `< ... >` clause without interpreting any of it, and both throw the clause away entirely, so nothing inside the angle brackets reaches the AST.
22. The declarator-level skip in `parseDirectAbstractDeclarator` is opt-in: it runs only when `ParserOptions::enableEffectAnnotations` is set, which `-enable-effect-annotations` does.
23. Because a `<` after a declarator is otherwise a generic argument list, the declarator-level skip disambiguates first.
24. A `<let` prefix and a `< X :` prefix are still generic argument lists.
25. Otherwise it scans ahead on a scratch `TokenReader` for a `;` before the next `>`; finding one identifies the clause as an annotation, so the parser commits the scratch reader and reads the `>`.
26. Finding no `;` leaves the tokens for the generic-argument path.
27. The semantic-level skip in `_parseOptSemantics` is unconditional: after a semantic such as `: SV_Position`, a following `<` is always treated as an annotation and every token up to the next `>` is advanced past, with no flag and no disambiguation.

**`### Error recovery`**

28. On an unexpected token, `Unexpected` emits a diagnostic through the `DiagnosticSink` and sets `Parser::isRecovering`.
29. While `isRecovering` is set no further unexpected-token diagnostic is reported, and it is cleared as soon as a token the parser was waiting for turns up.
30. `TryRecover` takes a recover-before set (tokens to stop in front of, leaving them unconsumed) and a recover-after set (tokens to consume and then continue past).
31. The default strategy used inside `{ ... }` blocks is recover-before `}` and recover-after `;`.
32. Skipping is done a balanced group at a time by `SkipBalancedToken`, so a bracketed or braced region is stepped over whole rather than token-by-token.
33. `TryRecover` refuses to skip past a closing token (`)`, `]`, `}`, end-of-file) unless a closing token is itself what it is looking for.
34. The AST is built best-effort even after errors so that downstream tools can still operate on a partial tree.
35. That block strategy is the only place a recover-after set is used; every other recovery site goes through `TryRecoverBefore`, which passes a single recover-before token and no recover-after set at all.
36. `Parser::readTokenImpl` recovers before the token it was expecting only once `isRecovering` is already set, or when the expected token is a `}` / `)` / `]` read through `ReadMatchingToken`; a first unexpected token in a `ReadToken` call is reported and left in place.
37. `AdvanceIfMatch` recovers before the enclosing region's closing token but abandons the search when the next token is in that region's bail set, so a parameter list, an initializer list, and a declaration position inherit the closing token of whichever matched region encloses them.

**`## AST data model`**

38. The AST is a strongly-typed C++ class hierarchy rooted at `NodeBase`.
39. The FIDDLE-generated code provides visitor dispatch, the `SyntaxClass` reflection metadata, and serialization support, and the generated files must not be edited by hand.

**`### The major node families`**

40. `Decl` is the declaration family, with concrete classes such as `ContainerDecl`, `FunctionDeclBase`, `VarDecl`, `AggTypeDecl`, `GenericDecl`, `ExtensionDecl`, and `InterfaceDecl`.
41. `Expr` is the expression family.
42. `Stmt` is the statement family, including `UnparsedStmt` for the deferred-body case.
43. `Type` is the type family, and `Type` derives from `Val`, so a type is itself a compile-time value.
44. `Modifier` is the family of qualifiers and attributes attached to decls.
45. `Val` is the family of compile-time values used by generics, and its user-level surface is a generic value argument — the `3` in `vector<float, 3>` and the `4` in `int a[4]`.
46. In a freshly-parsed AST both types and expressions use `Expr` representation, since at parse time `A(B)` could resolve to a function call or a type construction.
47. The semantic checker is what re-classifies them.
48. An `InvokeExpr` whose callee is a builtin arithmetic / comparison / bitwise / shift / unary operator over builtin scalar, vector, or matrix operands is converted to a `BuiltinOperatorExpr` by `convertToBuiltinArithmeticOp`, which records the resolved `BuiltinOperationKind` so the operator-name-to-kind mapping happens exactly once for constant folding, IR lowering, and for-loop trip-count inference; the node is synthesized during checking, not produced by the parser.
49. AST node casts use the templated `as<T>` helpers, which dispatch on the FIDDLE-generated `SyntaxClass` metadata rather than C++ RTTI.

**`### ASTBuilder`**

50. `ASTBuilder` owns allocation: AST nodes are arena-allocated through the builder so that lifetime tracks the owning module / session.
51. `ASTBuilder` owns hash-consing of types, so two structurally-identical types are represented by the same `Type*` pointer.
52. `create<T>()` allocates a fresh node and is what the parser calls for declarations, expressions, and statements; a `Val` type fails to compile there, rejected by a `static_assert`.
53. Anything in the `Val` / `DeclRef` world goes through `getOrCreate<T>()`, which keys the node on its operands in the `m_cachedNodes` dictionary and returns the existing node on a hit.
54. `getTypeCastIntVal` unwraps a nested `TypeCastIntVal`, tries to constant-fold the cast, and drops the cast entirely when the operand already has the target type.
55. Interning is visible from Slang source as type identity: `float3` and `vector<float, 3>` intern to the same `Type*`, so `int probe(float3 v)` and `int probe(vector<float, 3> v)` are one signature and the second is a redeclaration rather than a second overload.
56. Because `ASTBuilder*` is needed to construct any AST node, the builder pointer is threaded through every parsing helper that produces a node.

**`## Generics ambiguity`**

57. A bare `<` after an identifier is syntactically ambiguous: it can start a generic argument list or be the less-than operator.
58. `tryParseGenericApp` speculates on a copy of the `Parser` with a throwaway `DiagnosticSink`, so the real token reader never moves.
59. Only if the speculative parse is error-free and the token that follows the closing `>` is in the generic-application FOLLOW set — `::`, `.`, `(`, `)`, `[`, `]`, `:`, `,`, `?`, `;`, `==`, `!=`, `>`, `>>`, or end-of-file — does it reparse the generic application on the real parser.
60. Otherwise the `<` is still unread and ordinary infix parsing takes over; there is no single-token lookahead heuristic that suffices in all cases.
61. Generic declarations are unambiguous because declaration context tells the parser that `<` opens a parameter list; both a keyword-led declaration and a C-style function declarator such as `float f<T>(T x)` end up introducing a `GenericDecl`.
62. An optional `where` clause may follow the parameter list to attach type constraints, and parsing only records the syntactic form.
63. Constraints are parsed by `parseOptionalGenericConstraints` (the inheritance-clause form `: Base1, Base2`) and `maybeParseGenericConstraints` (the `where` form), each producing `GenericTypeConstraintDecl` members.
64. For a generic those constraint decls are siblings of the parameters under the enclosing `GenericDecl`, and `parseOptionalGenericConstraints` takes an optional `constraintTarget` parameter decoupling the constrained subject from the container the decls are added to.
65. A type/witness bound (`T : IBar`, `T == U`) produces a `GenericTypeConstraintDecl`, and the `==` spelling sets `isEqualityConstraint`.
66. The `:` spelling accepts a comma-separated list of bounds and produces one decl per bound.
67. `nonempty(Pack)` produces a `NonEmptyPackConstraintDecl`.
68. `countof(Pack) == IntExpr` produces a `GenericVariadicPackCountConstraintDecl`.
69. The reversed form `IntExpr == countof(Pack)` is detected and rejected with `Diagnostics::VariadicPackCountConstraintRequiresCountofOnLeft` rather than misread as an unrelated type constraint.
70. `__hasDiffTypeInfo(T)` produces a `HasDiffTypeInfoConstraintDecl`.
71. A coercibility bound `To(From)` produces a `TypeCoercionConstraintDecl`, with a trailing `implicit` keyword attaching an `ImplicitConversionModifier`.
72. The type/witness, `nonempty`, and `countof` forms may be prefixed with `optional`, which attaches an `OptionalConstraintModifier`.
73. `optional` on a `__hasDiffTypeInfo` clause is rejected with `Diagnostics::OptionalHasDiffTypeInfoConstraintIsInvalid`.
74. `FuncConstraintDecl` is a `GenericTypeConstraintDecl` subclass the parser never produces; header checking synthesizes it as a sibling requirement when an interface's callable requirement must itself be constrained as a type.

**`### Interface associated-type and __constraint requirements`**

75. An `associatedtype`'s constraints, whether written as an inheritance clause or as a `where` clause, are relocated to the enclosing `InterfaceDecl` so that they become interface-level requirements, siblings of the associated type.
76. `parseAssocType` detects the enclosing interface through `parser->currentScope` and passes it as the `constraintTarget`.
77. This yields the same representation as the `__constraint` syntax-as-declaration form.
78. `__constraint` is registered in the syntax-parse table and handled by `parseInterfaceConstraintDecl`, which parses the subject type, then either `==` (setting `isEqualityConstraint`) or `:` (a subtype requirement), then the bound type.
79. Where a `__constraint` is legal is enforced centrally by `isDeclAllowed`, which permits a `GenericTypeConstraintDecl` only as a member of an `InterfaceDecl` or a `GenericDecl`.

**`## Modifier parsing`**

80. Modifiers and attributes attach to a `Decl` through the `Modifier` chain rooted at `ModifiableSyntaxNode`.
81. `ParseModifiers` collects modifier tokens before the declaration keyword, dispatching keyword modifiers through the syntax-decl lookup and `[...]` groups through `ParseSquareBracketAttributes`.
82. Semantic checking later validates modifiers against the kind of declaration they modify, so `[unroll]` written in front of a function parses without complaint and the only diagnostic is `Diagnostics::AttributeNotApplicable` (E31002, "attribute 'unroll' is not valid here").
83. `Parser::ParseStruct` parses a bracketed attribute list written after the `struct` keyword but gates it on the module's language version, silently accepting it before 2025.
84. At language version 2025 that placement is reported as `Diagnostics::DeprecatedBracketAttributesPlacement` (W31204).
85. From 2026 on it is reported as `Diagnostics::InvalidBracketAttributesPlacement` (E31205).
86. Attributes written before the keyword are unaffected by that gate.
87. Attribute parsing is modifier parsing in disguise — the `[name(args)]` tokens become an `AttributeBase` modifier — so an attribute needing its own semantics gets a dedicated `Attribute` subclass, such as `NoDiscardAttribute`, whose `[NoDiscard]` causes the checker to error when a call to the marked function appears in a result-discarding context.

**`## Failure modes`**

88. Token-level errors not previously reported by the lexer surface here as parse errors via the `DiagnosticSink`.
89. Heuristic disambiguation can be wrong, and in those cases the parser prefers to produce some AST and let the checker either succeed or emit a more specific error, rather than aborting parsing.
90. `maybeDiagnoseKeywordUsedAsName` warns `Diagnostics::KeywordUsedAsName` when a declarator name is a reserved type keyword (`struct`, `class`, `enum`, `typealias`, `typedef`).
91. Both that check and the operator-name rule run from the shared declarator path, so they cover `var`, `let`, parameter, field, and `typedef` declarations uniformly.
92. An `operator <op>` name is only legal for a function: `UnwrapDeclarator` reports `Diagnostics::OperatorNameOnNonFunction` unless the caller opted in with `allowOperatorName`, which only the function branch of `ParseDeclaratorDecl` does.
93. So `V operator+(V a, V b) { ... }` is accepted while `int operator+ = 3;` draws `Diagnostics::OperatorNameOnNonFunction` (E20020), and the variable, parameter, `typedef`, and property cases are rejected without a per-kind test.
94. A malformed `operator <garbage>` is not flagged twice — it has already produced `Diagnostics::InvalidOperator`.
95. `Parser::parseVarDeclrStatement` keeps a declaration parsed inside a function body only if it is a `VarDeclBase`, a `DeclGroup`, an `AggTypeDecl` (`struct`, `class`, `enum`, `interface`), a `TypeDefDecl`, or a `using`.
96. Anything else written inside a function body — a `namespace`, for example — is reported with `Diagnostics::DeclNotAllowed` (E30102, "namespace is not allowed here."), a separate mechanism from the container-nesting check `isDeclAllowed` performs.
97. `parseFloatingPointLiteralExpr` maps the `FloatingPointLiteralType` classification onto the literal's `suffixType` (`Half` / `Float` / `Double`) or to a diagnostic (`InvalidFloatingPointLiteralNumber` for a bad significand, `InvalidFloatingPointLiteralSuffix` for an unrecognized suffix).
98. Range and precision problems are reported as `FloatLiteralTooSmall`, `FloatLiteralUnrepresentable`, or `FloatHexLiteralPrecisionLost`.
99. The parser reports at most one of these per literal: a single `diagnosed` flag guards the later arms, so the classification reports come first, then the range pair, then the precision report.
100.  The only way to trip two conditions is a classification failure that is also flagged out of range — `1e400q` — and there the suffix report wins and the range report is suppressed.
101.  The parser stores the value the helper returned; it does no clamping or truncation of its own.
102.  `parseIntegerLiteralExpr` splits the suffix into a width part (`l` / `L`, `ll` / `LL`, `z` / `Z`) and an unsigned part (`u` / `U`), and repeating either draws `Diagnostics::InvalidIntegerLiteralSuffix`.
103.  The pointer-width suffix `z` selects `intptr_t`, or `uintptr_t` when `u` is also present, and for a non-decimal literal it does so without consulting the magnitude at all, so `0xFFz` is `intptr_t`.
104.  For a decimal `z` or `ll` literal with no `u`, a value up to `INT64_MAX` is signed, and exactly `INT64_MAX + 1` is typed unsigned but marked `signedMinimumIntException`, which lets a surrounding unary `-` rewrite the type back to `intptr_t` / `int64_t`.
105.  `INT64_MAX + 2` and above warns `Diagnostics::IntegerLiteralTooLarge` (W40004) and stays unsigned.
106.  The grammar that the parser actually accepts is reverse-engineered in `../syntax-reference/grammar.md`.
