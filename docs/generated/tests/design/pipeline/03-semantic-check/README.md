# Tests for design/pipeline/03-semantic-check

## Intent

This bundle exercises the semantic-checking stage described in
[`docs/generated/design/pipeline/03-semantic-check.md`](../../../../design/pipeline/03-semantic-check.md):
turning a raw AST into a fully resolved, type-checked AST that AST-to-IR
lowering can consume. The doc is part architecture and part behavioural
contract; every test here is anchored to one of its behavioural claims. The
claim families it commits to are the output contract (names resolved to
canonical decls, types attached to every expression), the two-pass handoff
where the checker re-enters the parser to disambiguate `<`, the concern split
across the `slang-check-*.cpp` family, decl-refs as decl-plus-substitution,
generic specialization and constraint solving (the three associated-type
constraint spellings, the `==` equality constraint and its benevolent cycle,
the bare-`This` carve-out, the enum tag witness, and the six kinds of deferred
generic-argument-inference failure), differentiability modelled as an interface
conformance, check-time synthesis of constructors and conformance witnesses,
modifier and attribute validation, entry-point validation (capability
requirements of generic structs, unspecialized generic entry points, depth-output
conflicts, system-value semantic type compatibility, ignored binding modifiers),
and the failure-mode diagnostics the doc calls out by name.

Coverage strategy: one test per claim plus the edges the doc itself names — all
three constraint spellings rather than one, every enumerated inference-failure
kind rather than a representative, both the sign-coercion and the
category/shape rejections of the semantic-compatibility rule, both the gated and
ungated ignored-binding-modifier cases, and both sides of every gate (the
generic-struct requirement is tested satisfied as well as violated, the
`vk::binding` report is tested silent as well as fired, one depth output is
tested accepted as well as two rejected).

Semantic checking happens before any back-end codegen, so almost every claim is
target-independent: value observations use `//TEST:INTERPRET` (or CPU
`COMPARE_COMPUTE` where differential pairs and buffers are involved) and
rejection claims use `//DIAGNOSTIC_TEST:SIMPLE` citing the diagnostic code. No
per-target emission fan-out is warranted for those. The few claims that are
genuinely target-sensitive — the capability validation of a generic struct in an
entry-point signature and the target gate on `[[vk::binding(...)]]` — carry a
directive per relevant target instead.

**`## Inputs and outputs`**

1. The input is an AST produced by parsing, with function bodies still in `UnparsedStmt` form.
2. The output has names resolved: every `DeclRef`-bearing node points at the canonical decl.
3. The output has types attached: every `Expr` carries a `Type*`.
4. The output has conformances recorded, as in the `S : IFoo` witness table of the worked example.
5. The output has modifiers validated.
6. The output has default conformance witnesses synthesized, as in the `twice` slot the conformer never spelled.
7. The output has function bodies fully parsed and checked — the `UnparsedStmt` becomes a checked `Stmt` tree.
8. In the worked example, `IFoo` in `S`'s base list and in `T`'s constraint resolve to the same decl, and `v.twice()` gets the type `int`, which is what makes the call legal.
9. The result is the input to AST → IR lowering.

**`## SemanticsVisitor`**

10. The checker is a family of visitor subclasses that share state through `SemanticsContext`, with `SemanticsVisitor : public SemanticsContext` as the base.
11. `checkTranslationUnit` is the top-level entry point, called once per `TranslationUnitRequest` after parsing has collected the decls.

**`### Files and responsibilities`**

12. `slang-check.cpp` is the entry point that sequences the checking phases and emits no diagnostics about the program.
13. `slang-check-decl.cpp` checks decls and rejects a declaration conflicting with an earlier one (`E30200`).
14. `slang-check-expr.cpp` checks exprs and rejects assigning to something that is not an l-value (`E30011`).
15. `slang-check-stmt.cpp` checks stmts and rejects `break` outside a loop or `switch` (`E30003`).
16. `slang-check-type.cpp` resolves `Type` references in `Expr` form and rejects an expression used where a type is required (`E30060`).
17. `slang-check-overload.cpp` ranks overload candidates and emits the note naming the argument that rejected a candidate (`E40018`).
18. `slang-check-conformance.cpp` verifies and synthesizes conformances and emits no diagnostics; a missing requirement is reported as `E38100` by its caller in `slang-check-decl.cpp`.
19. `slang-check-conversion.cpp` ranks implicit conversions and rejects too many initializers in an initializer list (`E30523`).
20. `slang-check-inheritance.cpp` handles inheritance and extension lookup and rejects a circular `extension` (`E30815`).
21. `slang-check-modifier.cpp` validates modifiers and rejects two modifiers from one exclusive group on a decl (`E31202`).
22. `slang-check-constraint.cpp` solves generic constraints and rejects a pack count that fails a `countof(...)` constraint (`E30433`).
23. `slang-check-resolve-val.cpp` resolves and canonicalizes `Type`, `DeclRef` and witness values and emits no diagnostics.
24. `slang-check-shader.cpp` performs entry-point checks and rejects an entry point with no stage (`E38007`).

**`## Two-pass interaction with the parser`**

25. When the checker reaches an `UnparsedStmt` it calls `parseUnparsedStmt` with a `SemanticsVisitor*` so the parser can call back into the checker to disambiguate `<` tokens at parse time.
26. Once the body is parsed the checker continues normally over the resulting `Stmt` tree, so there is no clean parse / check boundary inside function bodies.

**`## Name lookup and DeclRef`**

27. Name resolution produces `DeclRef`s — a decl plus a substitution recording how its generic and outer-context parameters have been bound.
28. The algorithmic rules — scope construction, lookup, shadowing, visibility filtering, overload resolution — live in the `name-resolution` subtree.

**`## Generic specialization and constraints`**

29. Generic-parameter resolution is implemented across constraint accumulation/solving, witness finding/synthesis, and post-resolution `Val` validation.
30. `TryCheckOverloadCandidateConstraints` routes an outermost generic's defaulted and witness arguments through the constraint solver's fixpoint, the same path used for inferred arguments.
31. Only the explicitly supplied ordinary-argument prefix is passed as fixed caller input, so a user-written self-reference argument is not overwritten by a parameter's default.
32. On solver failure the code falls through to a per-constraint linear pass that re-derives the failing constraint to emit a precise diagnostic.
33. `associatedtype A : IBar` is recorded as a `GenericTypeConstraintDecl` requirement of the enclosing interface, a sibling of `A` rather than nested under it.
34. `associatedtype A where A : IBar` is recorded in that same unified representation.
35. A standalone `__constraint A : IBar` is recorded in that same unified representation.
36. `findWitnessForInterfaceRequirement` satisfies an interface-level constraint requirement by re-checking the subtype (or, for `==`, type-equality) relationship after `This` has been replaced by the conforming type, rather than by finding a member of that type.
37. A witness already installed by conformance synthesis — an `enum`'s `__Tag : __BuiltinIntegerType` — is honored by the witness-table early-out.
38. In the `bool`-tagged case no real subtype witness exists and a `NoneWitness` marks the compiler-trusted constraint satisfied.
39. Linearized inheritance lists are computed by `getInheritanceInfo` / `_calcInheritanceInfo`.
40. When computing the inheritance of an associated-type access such as `T.D`, the engine surfaces interface-level `__constraint`s, re-expresses each through the anchor's conformance witness, and adds the opposite endpoint as a base of the access.
41. An equality constraint `__constraint A == B` makes `T.A` and `T.B` mutual bases — a benevolent cycle.
42. The engine tolerates that cycle by skipping a base whose inheritance info is still being computed; a frame whose skipped set is non-empty after subtracting itself is contextual, is not cached, and is recomputed by a later root-level query.
43. A bare-`This` subject on an interface `__constraint` is rejected during checking because it would express inheritance rather than a checked predicate.
44. When a generic cannot be specialized for a call the failure reason is captured eagerly as a `GenericArgumentInferenceFailure` and reported lazily, its `Kind` selecting both payload and diagnostic.
45. `VariadicPackCountMismatch` emits `E30433`, triggered by `takesTwo(1, 2, 3)` against `void takesTwo<each T>(expand each T args) where countof(T) == 2`.
46. `GenericArityMismatch` emits `E30438`, triggered by a call whose argument list cannot be matched to the generic's parameter list at all.
47. `OrdinaryGenericParamNotInferred` emits `E30439`, triggered by `f(1)` against `void f<T>(int a)`.
48. `InterfaceConformanceNotSatisfied` emits `E38029`, triggered by `pick(s)` against `T pick<T : IFoo>(T a)` where `S` does not implement `IFoo`.
49. `GenericConstraintNotSatisfied` emits `E30440`, triggered by `f(1.5f)` against `void f<T>(T a) where T == int`, and is the fallback for every constraint that is not a conformance.
50. `GenericParamUnificationConflict` emits `E30442`, triggered by `two(x, y)` against `void two<T>(T a, T b)` with unrelated `A` and `B`.
51. Every arm follows its error with a "see declaration of" note carrying the candidate's rendered signature.
52. The `GenericConstraintNotSatisfied` arm adds a second note pointing at the `where`-clause.
53. Each `Kind` stores only the offending fields and the expensive message formatting is deferred so speculative candidates never pay for it.
54. The failure is attached to the `OverloadCandidate` and turned into a focused diagnostic only if overload resolution selects that failed candidate.
55. Before this mechanism every specialization failure collapsed into the catch-all `GenericArgumentInferenceFailed`.

**`### Differentiability as interface conformance`**

56. `[Differentiable]` parses to a `BackwardDifferentiableAttribute`.
57. On seeing that attribute or a `ForwardDifferentiableAttribute` the checker synthesizes `extension __func_as_type(f) : IForwardDifferentiable<__func_as_type(f)>` and gives it the `fwd_diff` member the interface requires.
58. The synthesized `fwd_diff` is itself given the same pair of conformances, which is what makes higher-order differentiation resolve through ordinary lookup.
59. The interface types are built by `getForwardDiffFuncInterfaceType` / `getBackwardDiffFuncInterfaceType`, which pair the base function type with the `__hasDiffTypeInfo` witness the interfaces demand.
60. Asking "is this callee differentiable?" is a subtype query: `isFuncForwardDifferentiable` / `isFuncBackwardDifferentiable` return the `SubtypeWitness*` that `tryGetSubtypeWitness` produced, because the caller needs that witness to build and specialize the derivative call.
61. A `[Differentiable]` annotation on an interface requirement is handled as a requirement of the enclosing interface rather than something nested under the member.
62. `_moveInterfaceDifferentiabilityRequirementToInterface` starts the `GenericTypeConstraintDecl` under the callable that owns the generic environment its type mentions, then hoists it into a standalone requirement directly under the interface.
63. The explicit `__func_extension fwd_diff(foo)(...)` spelling is rewritten into `extension foo : IForwardDifferentiable<foo>` with the user's body as the `fwd_diff` member.

**`## Synthesizing implicit code`**

64. Some declarations gain members at check time rather than parse time: default conformance witnesses, generated comparison / construction methods, and several built-in conformances.
65. The decisions live in `slang-check-decl.cpp` while `slang-ast-synthesis.cpp` supplies the `ASTSynthesizer` helpers that build the AST fragments.

**`## Modifier validation`**

66. Modifier validation covers which modifiers are allowed on which decls, mutually exclusive combinations, attribute argument types, and the differences between Slang and GLSL input.
67. `getModifierConflictGroupKind` maps a modifier's `ASTNodeType` to the group it competes in, and a second modifier landing in a group already claimed on the same decl produces `E31202`.
68. Most modifiers are their own group, so a plain repeat such as `static static int g;` is the common case.
69. `out`, `inout`, `ref` and `borrow` share a group.
70. `static` and `uniform` share a group.
71. `nointerpolation`, `noperspective`, `linear`, `sample` and `centroid` share a group.
72. `checkModifier` computes `isGLSLInput` from the `-allow-glsl` option or a `GLSLModuleModifier` on the module and passes it to `isModifierAllowedOnDecl`; a modifier used in a position that predicate rejects is reported as `E31201`.
73. Only a few entries branch on that flag — `globallycoherent` and `volatile` are additionally allowed on the fields of a global struct when `isGLSLInput` holds.

**`### Visibility scopes`**

74. `public` is visible from any scope, including other modules.
75. `internal` is visible from any scope in the declaring module.
76. `private` is visible from the declaring type or namespace, plus extensions of that same type.
77. `private` is therefore type-scoped, not file-scoped: a free function in the same file cannot read a `private` member of a `struct`, and the read is rejected with `E30600`.
78. Writing `private` where there is no enclosing type for it to scope to — at global scope, or on an interface requirement — is rejected up front with `E30603`.

**`### dyn interface restrictions`**

79. The `dyn interface` validations are a no-op unless the module's language version is 2026 or later (`-std 2026`) *and* `-enable-experimental-dynamic-dispatch` was not passed, so the same source compiles differently under the default `-std`.
80. With the gate open the interface may not be generic (`E33072`).
81. It may not declare an associated type (`E33073`).
82. It may not declare a generic method (`E33074`).
83. It may not declare a `[mutating]` method (`E33075`).
84. It may not declare a `[Differentiable]` method (`E33076`).
85. It may not declare a non-`dyn` base interface (`E33077`).
86. A conforming type may not acquire the conformance through an `extension` (`E33078`).
87. A conforming type may not be generic (`E33082`).
88. A conforming type's fields may not be unsized (`E33079`).
89. A conforming type's fields may not be opaque (`E33080`).
90. A conforming type's fields may not be non-copyable (`E33081`) — the dynamic representation has to be a copyable, fixed-size box.

**`## Shader-specific checks`**

91. Entry-point validation covers the function's stage attribute, parameter modifiers, return-type compatibility with the stage, and resource binding rules.
92. `collectGenericStructTypeUses` recurses through an entry point's signature types to find every user-defined generic struct — including nested inside `Optional<...>`, arrays, or `ConstantBuffer<...>` — and validates its `[require(...)]` against the target.
93. The general capability-inference walk records a type's requirements only for a `DirectDeclRef`, so a generic specialization is skipped and the requirement would otherwise be dropped.
94. Builtin generic types carrying `MagicTypeModifier` / `IntrinsicTypeModifier` are filtered out of that check but still recursed through.
95. A requirement the target cannot provide — `[require(cpp)] struct Foo<T>` named as `Foo<int>` in a SPIR-V entry point's signature — is reported against the entry point as `E36107`, followed by a `see using of 'Foo'` note.
96. A generic entry point left genuinely unspecialized lowers to an `IRGeneric` rather than an `IRFunc`; `diagnoseGenericEntryPoint` emits `E38014` against the entry-point name only for the truly-unspecialized case.
97. `collectDepthOutputSemantics` walks every `out` / `inout` parameter and the return type, unwrapping `Conditional<T>` and array wrappers and recursing into struct fields.
98. A collected depth-semantic count above one produces `E30705`, naming the second contributor as conflicting with the first.
99. `isSemanticTypeCompatible` accepts two types when they have the same shape — both scalar, or both vectors of equal element count — and their scalar element types fall in the same category (integer, floating-point, or bool).
100. That admits sign coercions such as `int3` for a `uint3` semantic.
101. It rejects cross-category cases such as `float gi : SV_GroupIndex` with `E30701`.
102. It rejects shape mismatches such as `float pos : SV_Position` with `E30701`, whose message lists the types the semantic will accept.
103. Entry-point parameter checking reports `E38010` — naming the modifier and the parameter and saying it will be ignored — for `[[vk::binding(...)]]`, `[[vk::push_constant]]`, `register()` and `packoffset()`.
104. Only the `[[vk::binding(...)]]` case is gated, by `_allTargetsSupportVkBindingOnEntryPointParameters` over all of the linkage's targets and by `isVkBindingCompatibleEntryPointParameterType` for the parameter's own type, so that it fires only where the attribute really would be dropped.
105. `[[vk::push_constant]]`, `register()` and `packoffset()` are diagnosed unconditionally when found on an entry-point parameter.

**`## Failure modes`**

106. All semantic-checking errors flow through the `DiagnosticSink` threaded into `SemanticsContext`.
107. Check-level recovery is "continue with a placeholder type": unresolved decls become `ErrorType`-typed and overload resolution returns a synthetic `errorExpr` rather than aborting.
108. `ExpectATypeRepr` builds the `ExpectedAType` message from the expression's actual type and, when available, the referenced name.
109. A call matching no overload reports `E39999` on the call, then an `E40011` `candidate: <signature>` note per candidate, each followed by an `E40018` note reading `argument 0 does not match: expected 'A', got 'float'`.
110. Candidates are deduplicated by their rendered signature string, not by `Decl*`, which would wrongly collapse distinct specializations such as `foo<float>` and `foo<int>`.
111. At most ten unique candidates are printed and the remainder are summarized by an `E40015` "N more overload candidates" note.
112. A conservative similar-name suggestion is attached to the existing `E30015` undefined-identifier diagnostic rather than emitted as a detached note.
113. `findClosestInScopeName` suggests nothing for a name under 3 or over 256 characters, allows a distance of `min(3, max(1, length / 3))`, skips core-module declarations and anything the scope could not access, and suppresses the suggestion when two distinct names tie.
114. `myLongVariableNam` suggests `myLongVariableName`.
115. `ac` does not suggest the in-scope `ab`.
116. `sqr` does not suggest the core module's `sqrt`.
117. `maybeDiagnoseDiscardedNoDiscardResult` fires with `E30059` when the result of a `[NoDiscard]` call is thrown away as a bare expression statement, recursing through comma, ternary-select and short-circuit forms to find the discarded sub-expression.
118. A bare discarded constructor call is deliberately excluded from that check.
119. `checkModule` drives every `Decl` in the translation unit through the `DeclCheckState` sequence up to `CapabilityChecked`, with no separate errored state, so recovery is expressed as diagnostics plus error types / expressions substituted in place.
