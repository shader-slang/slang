# Tests for design/pipeline/03-semantic-check

## Intent

This bundle exercises the semantic-checking stage described in
[`docs/generated/design/pipeline/03-semantic-check.md`](../../../../design/pipeline/03-semantic-check.md):
turning a raw AST into a fully resolved, type-checked AST that AST-to-IR
lowering can consume. The doc is part architecture and part behavioural
contract; every test here is anchored to one of its behavioural claims. The
claim families it commits to are the output contract (names resolved to
canonical decls, types attached to every expression), the two-pass handoff
where the checker re-enters the parser to disambiguate `<`, the concern split
across the `slang-check-*.cpp` family, decl-refs as decl-plus-substitution,
generic specialization and constraint solving (the three associated-type
constraint spellings, the `==` equality constraint and its benevolent cycle,
the bare-`This` carve-out, the enum tag witness, and the six kinds of deferred
generic-argument-inference failure), differentiability modelled as an interface
conformance, check-time synthesis of constructors and conformance witnesses,
modifier and attribute validation, entry-point validation (capability
requirements of generic structs, unspecialized generic entry points, depth-output
conflicts, system-value semantic type compatibility, ignored binding modifiers),
and the failure-mode diagnostics the doc calls out by name.

Coverage strategy: one test per claim plus the edges the doc itself names — all
three constraint spellings rather than one, every enumerated inference-failure
kind rather than a representative, both the sign-coercion and the
category/shape rejections of the semantic-compatibility rule, both the gated and
ungated ignored-binding-modifier cases, and both sides of every gate (the
generic-struct requirement is tested satisfied as well as violated, the
`vk::binding` report is tested silent as well as fired, one depth output is
tested accepted as well as two rejected).

Semantic checking happens before any back-end codegen, so almost every claim is
target-independent: value observations use `//TEST:INTERPRET` (or CPU
`COMPARE_COMPUTE` where differential pairs and buffers are involved) and
rejection claims use `//DIAGNOSTIC_TEST:SIMPLE` citing the diagnostic code. No
per-target emission fan-out is warranted for those. The few claims that are
genuinely target-sensitive — the capability validation of a generic struct in an
entry-point signature and the target gate on `[[vk::binding(...)]]` — carry a
directive per relevant target instead.
