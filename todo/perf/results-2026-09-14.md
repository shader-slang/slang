# Hash map and hash function selection: results

Supersedes `matrix-results-2026-09-13.md`, whose numbers were taken before the phase 1 and 2
hashing work landed and before nine order-dependence defects were fixed. That note's own warning
-- do not pick a default from it -- still stands; this one is written to be picked from.

**Recommendation: `SLANG_HASHMAP=BOOST_FLAT`, `SLANG_HASH=WYHASH`**, or `GTL_FLAT` with the same
hash if boost is too heavy a dependency to take on. The two are 0.8% apart.

Against master that is **4.1% on the geometric mean over workloads, 1.8% on the suite's total
time**. The difference between those two figures is not noise and is worth carrying whenever
either is quoted: the change makes 30 of 33 workloads faster, by a median of 3.5%, but the two
heaviest workloads in the suite are a downstream PTX compile and generic semantic checking, and
neither is touched by any of this. Section 5 has the distribution. The nearest thing to a single
honest number is the one real shader in the suite, `mdl_dxr`, at 0.963x.

---

## 1. What was measured

Three runs, each with `extras/bench-loop.sh`, which measures every compile-perf workload against
every build in a shuffled order, reshuffling each pass, with the builds for a given workload run
back to back so that a comparison between them is not separated by machine drift.

| Run                                   | Builds | Passes | Purpose                                        |
| ------------------------------------- | ------ | ------ | ---------------------------------------------- |
| `maps-2026-09-14`                     | 22     | 5      | screen 12 maps and 6 hashes                     |
| `top5-2026-09-14`                     | 6      | 8      | separate the finalists                          |
| `i03-pre03-master-2026-09-14`         | 7      | 3      | total impact, and what the HashSet change added |

Ratios are the geometric mean of paired per-workload, per-pass ratios; intervals are a bootstrap
over those pairs. Lower is faster. All builds are Release; the metric is `compileInner`, the whole
compile excluding the fixed core-module load.

## 2. The map is what matters

Twelve maps at the `wyhash` hash, five passes, 153 paired observations each:

| Map                         |  Ratio | 95% CI         |
| --------------------------- | -----: | -------------- |
| `boost_flat`                | 0.956x | [0.952, 0.959] |
| `gtl_flat`                  | 0.972x | [0.968, 0.976] |
| `absl_flat`                 | 0.982x | [0.976, 0.987] |
| `unordered_dense` (current) | 1.000x | --             |
| `tsl_robin`                 | 1.006x | [1.000, 1.012] |
| `boost_node`                | 1.035x | [1.025, 1.047] |
| `absl_node`                 | 1.069x | [1.056, 1.084] |
| `tsl_hopscotch`             | 1.103x | [1.095, 1.111] |
| `std`                       | 1.118x | [1.104, 1.137] |
| `boost_unordered`           | 1.128x | [1.112, 1.148] |
| `tsl_sparse`                | 1.196x | [1.181, 1.214] |
| `unordered_dense_segmented` | 1.357x | [1.303, 1.424] |

The flat, open-addressed maps take the top four places and the node-based ones lose, which is
what pointer chasing predicts. `unordered_dense_segmented` is much the worst: the extra
indirection its block list adds to every access is not repaid by the cheaper growth it buys.

`boost_flat` is faster on **33 of 33 workloads**, worst case 0.996x, best 0.882x. That is worth
stating separately from the average, because `absl_flat`'s 0.982x is not of the same kind: it is
faster on only 18 of 33 and loses on every `emit_*` workload, so its average hides real
regressions.

## 3. The hash function does not matter

Six hashes at `unordered_dense`:

| Hash        |  Ratio |
| ----------- | -----: |
| `boost`     | 0.994x |
| `std`       | 1.000x |
| `wyhash`    | 1.000x |
| `absl`      | 1.006x |
| `rapidhash` | 1.019x |
| `komihash`  | 1.104x |

Four of the six are within 0.6% of each other, which is the noise. Two are not: `komihash` is
10% slower and `rapidhash` 2% slower, so those two are worth avoiding, but among the rest there
is nothing to choose.

These builds postdate the `kHasUniformHash` fix (`nsurnmks`), without which `boost` and `std`
were telling the map to skip mixing a hash that needed it. Before that fix this row could not be
read.

### Map and hash are additive, with one exception

The cross cells agree with map-effect x hash-effect to within 0.7%:

| Combination                           | Predicted | Measured |  Error |
| ------------------------------------- | --------: | -------: | -----: |
| `absl-gtl_flat`                       |    0.978x |   0.972x |  -0.6% |
| `komihash-tsl_sparse`                 |    1.320x |   1.310x |  -0.7% |
| `rapidhash-tsl_hopscotch`             |    1.123x |   1.117x |  -0.6% |
| `rapidhash-unordered_dense_segmented` |    1.382x |   1.386x |  +0.3% |

The exception is `boost_flat`, where the hash makes no difference at all -- see below. Additivity
predicted `boost-boost_flat` at 0.950x; it measured 0.957x, the same as every other hash paired
with that map.

## 4. The finalists

Eight passes, ~235 paired observations each, compared directly against one another rather than
through a shared baseline:

| Comparison                                |             Ratio | Verdict     |
| ----------------------------------------- | ----------------: | ----------- |
| `boost-boost_flat` vs `std-boost_flat`    |  1.000x [.998,1.003] | same        |
| `std-boost_flat` vs `wyhash-boost_flat`   |  1.002x [.999,1.004] | same        |
| `boost-boost_flat` vs `wyhash-boost_flat` |  1.002x [.999,1.005] | same        |
| `absl-boost_flat` vs `wyhash-boost_flat`  | 1.004x [1.001,1.007] | wyhash ahead |
| `boost-gtl_flat` vs `wyhash-boost_flat`   | 1.007x [1.003,1.011] | boost_flat ahead |

**The hash is irrelevant to `boost_flat`.** `wyhash`, `std` and `boost` are indistinguishable;
only `absl` separates, by 0.4%. The mechanism fits: `boost_flat` remixes the hash itself, so the
quality of what it is given does not reach the probe.

## 5. Total impact, and what the HashSet change added

Three arms built from three commits and measured together: `master`, everything merged except the
HashSet change (`pre03`), and with it (`i03`).

| Build                   | vs master | 95% CI         |
| ----------------------- | --------: | -------------- |
| `i03-boost_flat`        |    0.959x | [0.952, 0.967] |
| `pre03-boost_flat`      |    0.967x | [0.960, 0.975] |
| `i03-gtl_flat`          |    0.968x | [0.962, 0.975] |
| `pre03-gtl_flat`        |    0.970x | [0.963, 0.976] |
| `pre03-unordered_dense` |    0.989x | [0.984, 0.994] |
| `i03-unordered_dense`   |    0.993x | [0.990, 0.997] |
| `master`                |    1.000x | --             |

**The whole body of work is worth 4.1%** against master, and the map swap is most of it: keeping
`unordered_dense` and taking only the algorithmic changes gives 1.1%.

### The 4.1% is broad, but it is not the wall clock

That 4.1% is a geometric mean over workloads, which weights a 5 ms workload the same as a 4 s one.
Added up as time instead, the suite goes from 11182 ms to 10979 ms, which is **1.8%**. Both are
honest and they answer different questions; quoting the first without the second overstates what a
user would feel.

The gap between them is two workloads:

| Workload       | master |  Ratio | Share of suite time |
| -------------- | -----: | -----: | ------------------: |
| `codegen_ptx`  | 4343ms | 1.004x |                 39% |
| `sema_generics`| 1522ms | 1.003x |                 14% |

Half the suite's clock is those two, and neither moves. For `codegen_ptx` that is expected --
most of its time is inside the downstream PTX compiler, which none of this touches. For
`sema_generics` it is a result in its own right: semantic checking of generics is the single most
expensive thing the suite does and hash containers are not what makes it slow. That is where to
look next.

Otherwise the change is uniform rather than concentrated: **30 of 33 workloads faster, median
0.965x**, best `module_link` at 0.866x, then `control_flow_ssa` 0.902x, `specialization` 0.928x,
`inlining` 0.932x, `autodiff` 0.944x. The three that are not faster -- `sema_generics` 1.003x,
`codegen_ptx` 1.004x, `minimal` 1.016x -- are all within the measurement's own spread, and
`minimal` is a 9.6 ms workload where that is a rounding error. Nothing regresses.

The single most representative number is `mdl_dxr`, the only real shader in the suite, at
**0.963x** -- almost exactly the median.

### Issue 03 is worth much less than its note predicted

| Map               | `i03` vs `pre03` | Verdict   |
| ----------------- | ---------------: | --------- |
| `unordered_dense` | 1.004x [.999,1.009] | no change |
| `boost_flat`      | 0.992x [.987,.996] | 0.8% faster |
| `gtl_flat`        | 0.998x [.995,1.002] | no change |

Halving the entry from 16 bytes to 8 helps only `boost_flat`, and only by 0.8%. Issue
[03](03-hashset-uses-dictionary-with-dummy-value.md) calls entry size "a first-order input to
flat-versus-node performance" and says halving it "systematically favours the flat maps"; two of
the three flat maps did not move. The likely reason is that `unordered_dense` and `gtl_flat` keep
their entries outside the bucket array -- a probe touches the buckets either way and the entry
size stays off the hot path -- while `boost_flat` stores entries in the slots and so is the one
that can benefit. **Issue 03 was carried through this work as the confound that might reorder the
maps. It does not: the ranking is identical with and without it.**

## 6. What it costs

| Option            | vs master | Dependency                          |
| ----------------- | --------: | ----------------------------------- |
| `boost_flat`      |    0.959x | boost: 9 modules, 22 MB             |
| `gtl_flat`        |    0.968x | gtl: 3.9 MB, header-only            |
| `unordered_dense` |    0.993x | current, already vendored           |

Dropping boost entirely costs 0.9 points of the 4.1. `boost::unordered` pulls `assert`, `config`,
`container_hash`, `core`, `describe`, `mp11`, `predef`, `throw_exception` and `unordered` into a
project that otherwise does not use boost; `gtl` is one header-only library a fifth of the size.
That is the decision, and it is a judgement about dependencies rather than about performance.

## 7. What these numbers do not say

- **The suite is mostly synthetic.** Its workloads each amplify one compiler pass, and its README
  is explicit that a ratio from them is a sensitivity figure for that pass rather than a
  user-facing speedup. The exception is `mdl_dxr`, a real shader, which did run this time and
  gave 0.960x for `boost_flat` -- close to the suite average, which is reassuring but is one
  workload.
- **Compile time only**, not generated code quality or runtime.
- **One machine.** Everything here is one Linux box with one GPU; nothing has been confirmed on
  another machine or another compiler.
- **The three-arm run has only 3 passes** where the others have 5 and 8, so its intervals are the
  widest here. It agrees with the finalist run where they overlap (`boost_flat` against
  `gtl_flat`: 0.993x there, 0.992x here).

## 8. Reproducing

```bash
extras/hashmap-matrix.sh --all                 # build the matrix
extras/bench-loop.sh --name my-run build-a build-b ...
```

`bench-loop.sh` writes to `~/work/tmp/bench-loop/<name>/`, records each measurement as it
finishes, and skips what is already recorded, so it can be interrupted and resumed. Run it with
nothing else on the machine: these are timings, and a build running alongside is
indistinguishable in the results from a slow combination.

The analysis scripts used for this note are in `~/work/tmp/` (`analyse-maps.py`, `pairwise.py`,
`analyse-interaction.py`, `analyse-workloads.py`). They are throwaway; the shape worth keeping is
that every comparison is paired within a workload and a pass.

## 9. Correctness work this rested on

The benchmark could not be run at all at the start: only `unordered_dense` produced a working
compiler. The other eleven maps exposed nine order-dependence defects, all of them present on
master and none in the hash map layer. `unordered_dense` is the only one of the twelve that
iterates in insertion order, and that happened to be the order the affected code wanted.

Two produced a compiler whose output changed between runs of the same binary on the same input:
the Metal nested-struct field order (ten compiles gave seven different orderings) and the
capability diagnostics. One made a SPIR-V compile emit the HLSL body of `Texture.Load`. The fixes
are in `todo/perf/matrix-results-2026-09-13.md` section 1, and all of them are on master's side of
this work rather than in anything measured here.

After them, all 32 combinations of the original matrix passed the full test suite in Release,
with every failure triaged individually at `-j1`: 85 such failures, all transient, none genuine.
