## Motivation

Slang silently accepts implicit integer → floating-point conversions that lose precision. Consider the program from #12929:

```slang
RWStructuredBuffer<float> output;
StructuredBuffer<int> input;
[shader("compute")]
void main() {
    output[0] = input[0];   // variable int -> float
    output[1] = 123;        // in range, fine
    output[2] = 123456789;  // becomes 123456792 -- silently loses precision
}
```

`output[2] = 123456789` compiles with no diagnostic even though `123456789` is not representable as a `float` (24-bit mantissa) and is rounded to `123456792`. `int64_t` → `double` has the same problem (53-bit mantissa). By contrast the truncating direction (`float` → `int`) already warns (E30081), and `float` → `double` warns at argument sites (E30082, gated to `CoercionSite::Argument`).

Root cause: `getBaseTypeConversionCost` costs every integer → float/double at `kConversionCost_IntegerToFloatConversion` (400), deliberately below the `kConversionCost_Default` (500) threshold the general `UnrecommendedImplicitConversion` (E30081) warning keys off — because `float` is the preferred integer → real target for overload ranking. So these conversions were never reached by any warning.

## Proposed solution

Add dedicated warnings in the `_coerce` diagnostic path (where E30081/E30082 already live), rather than raising the conversion cost — raising the cost would perturb overload resolution language-wide.

Two tiers, matching what can actually be proven at compile time:

- **Constant source, default-on** (E30133 float / E30135 double): warn only when the folded constant's exact value is not representable in the target mantissa. A constant that silently changes value is unambiguous, mirroring the existing constant-overflow warning; `float b = 123` and `float c = 268435456` (`2^28`, a power of two) stay silent.
- **Non-constant source, opt-in `-Wpedantic`** (E30134 float / E30136 double): a variable `int` → `float` cannot be proven lossy at compile time and is pervasive in real shader code, so a default-on warning could create substantial noise in existing code (and would trip existing clean-stderr tests). It lives in the off-by-default `pedantic` group, matching C/C++ `-Wconversion`, and only fires when the source integer type is wide enough to lose precision (`int32` → `double` is always exact and never warns).

> **Scope note (for a maintainer decision):** the reporter (@skiminki-nv) annotated the **variable** case `output[0] = input[0]` as "a warning should be emitted", so making the variable case opt-in rather than default-on is a conscious divergence from the literal request — chosen to avoid flooding existing shaders. Flipping the variable warnings to default-on is a small change (drop the `pedantic` tag from the two variable diagnostics E30134/E30136). Flagged here for a maintainer call.

## Concepts and vocabulary

- **`_coerce` diagnostic block** — the region of `SemanticsVisitor::_coerce` (guarded by `outToExpr && site != ExplicitCoercion`) that emits implicit-conversion diagnostics when a conversion is actually reified. Explicit casts set `ExplicitCoercion` and are exempt.
- **Mantissa representability** — an integer is exactly representable in a binary float with `p` mantissa bits iff the significant bits of its magnitude (after dropping trailing zeros) number ≤ `p`. So `2^28` (one significant bit) is exact in `float` even though it is 29 bits wide, but `2^24 + 1` is not.
- **Warning groups (`WarningLevel`)** — `Default` warnings always fire; `all`/`extra`/`pedantic` are groups enabled by `-Wall`/`-Wextra`/`-Wpedantic`. Of these, `extra` is on by default while `all` and `pedantic` are off by default (`slang-options.cpp`), so tagging the variable-source warnings `pedantic` makes them opt-in.

## Process report

**Diagnostics (`slang-diagnostics.lua`).** Four new warnings, codes 30133–30136 (the next free contiguous block). Constant forms use the default group; variable forms carry the `pedantic` sentinel. `int64_t` → `double` has its own message (53-bit mantissa), distinct from `float`'s 24-bit, per the mantissa difference. Fields `{fromType, toType, expr}` mirror the sibling `UnrecommendedImplicitConversion`.

**Helper `isIntExactlyRepresentableInFloat` (`slang-check-conversion.cpp`).** New, because no existing helper computes IEEE mantissa representability — `getIntValueBitSize` counts total significant bits *including* trailing zeros, which would false-positive on values like `2^28`. The helper strips trailing zeros from the magnitude and compares the remaining significant-bit count to the mantissa width. It takes `isSourceUnsigned` because `IntegerLiteralValue` is `int64_t`: an unsigned 64-bit constant (e.g. `0xFFFFFFFFFFFFFFFF`) stores its bit pattern and reads as `-1` when treated as signed, so its magnitude must be read from the unsigned bit pattern. Signedness comes from the source type via the existing `isSigned`.

**Emit block (`slang-check-conversion.cpp`).** An independent `if` after the `ImplicitConversionToDouble` special case (not nested in the cost bands, since these conversions cost 400 and never reach the `>= 500` branch). Input-shape check: the input is a genuine, canonical `int` → `float`/`double` coercion — the same shape E30081/E30082 already diagnose here — so the checker's coercion path is the correct layer; this is not papering over a malformed representation. It gates on `!isCoreModule` (the stdlib does many such conversions), computes the mantissa width from `toType` (`BasicExpressionType` base type `Float`/`Double`; vectors/matrices and `half` are skipped), and then:

- constant source (`getFoldedIntVal()` non-null) → representability check → default-on diagnostic;
- otherwise, a scalar integer source with `getMaximumTypeBitSize > mantissaBits` → opt-in diagnostic.

Both `float` → `double` (folds to no integer constant, and is not a scalar integer source) and `int32` → `double` (32 ≤ 53) are correctly excluded.

Addresses #12929 (constant-loss diagnostics land by default; the variable-source policy is left for a maintainer decision as noted above — deliberately not `Fixes`, to avoid auto-closing while that is open).

**Test (`tests/diagnostics/lossy-int-to-float-conversion.slang`).** Runs the compiler twice (default and `-Wpedantic`), exhaustively asserting: `123456789` → float, the constant *expression* `16777216 + 1` (`2^24 + 1`) → float, and `2^53 + 1` → double warn by default; `0xFFFFFFFFFFFFFFFF` → double warns (guards the unsigned path); the `2^24` exact boundary, representable/power-of-two constants, explicit casts, and `int32` → double stay silent; and the variable cases warn only under `-Wpedantic`.
