## Motivation

Slang's capability model collapsed two distinct SPIR-V fp16 atomic extensions into a single
requirement, so there was no way to ask for "half-vector atomics" specifically:

- `SPV_EXT_shader_atomic_float16_add` provides scalar `half` `OpAtomicFAdd` (capability
  `AtomicFloat16AddEXT`).
- `SPV_NV_shader_atomic_fp16_vector` provides `half2` / `half4` atomic add/sub/min/max/exchange
  (capability `AtomicFloat16VectorNV`).

Only the scalar atom existed, and the `GL_NV_shader_atomic_fp16_vector` alias carried a
`| _spirv_1_0` disjunct. That disjunct is the concrete bug: because plain SPIR-V 1.0 satisfies it,
the vector path type-checked on any SPIR-V target, whether or not the NV extension was available.
Consider this shader:

```slang
RWStructuredBuffer<half2> vectorBuffer;

[require(GL_NV_shader_atomic_fp16_vector)]
[numthreads(1, 1, 1)]
void computeMain()
{
    __atomic_add(vectorBuffer[0], half2(1.0h, 2.0h));
}
```

Before this change the `[require(...)]` was satisfiable by bare SPIR-V 1.0, so nothing forced the
`SPV_NV_shader_atomic_fp16_vector` extension to be declared and no diagnostic told the user their
target could not do this. Requesting a genuinely unsupported shape was equally quiet: a `half3`
atomic, or a compare-exchange on `half2`, had no representation in the NV extension but was not
rejected before SPIR-V emit.

## Proposed solution

Give the NV vector extension its own capability atom and make the implication explicit, so the
capability system — rather than emit-time guesswork — decides which path a program is allowed to
take:

```
def SPV_NV_shader_atomic_fp16_vector : _spirv_1_0;
def spvAtomicFloat16VectorNV : SPV_NV_shader_atomic_fp16_vector + spvAtomicFloat16AddEXT;
```

`spvAtomicFloat16VectorNV` implies `spvAtomicFloat16AddEXT` because a target providing the vector
extension also provides the scalar add. That implication is what lets `InterlockedAddF16` keep one
user-facing signature while dispatching to either path. The alias then drops the `| _spirv_1_0`
disjunct and gains `| spvAtomicFloat16VectorNV`, so requesting it means what it says.

This is the principled layer for the fix. The bug is not that emit produced wrong SPIR-V from
well-formed IR; it is that the *requirement graph* did not distinguish two different hardware
features, so the front end admitted programs the backend could not honor. Adding the atom fixes the
representation, and the unsupported width/operation cases become IR-validation diagnostics that fire
before emit rather than assertions or malformed output afterwards.

## Concepts and vocabulary

- **Capability atom vs alias** — an atom (`def`) is a leaf feature the compiler can require; an
  alias is a user-facing name resolving to a disjunction of atom conjunctions. A `| _spirv_1_0`
  disjunct makes an alias satisfiable by any SPIR-V target, which is why its presence here defeated
  the requirement.
- **`__target_switch` / `case <capability>:`** — dispatch in `.meta.slang` on the capabilities in
  effect, letting one intrinsic body serve several targets. Fall-through to `default:` is how the
  scalar path stays the base case.
- **Void-returning atomic** — front-end atomics like `InterlockedAddF16` return the original value
  through an `out` argument. SPIR-V legalization rewrites them so the IR instruction's own type is
  `void`, which means later passes cannot read the element type off the instruction and must recover
  it from the pointer operand. This is what `getAtomicOperationValueType()` exists for.

## Process report

**Why a new capability atom rather than a check at emit.** The failure was admission, not
translation: the requirement graph could not express "needs NV vector atomics", so the front end
accepted programs whose only correct outcome was a backend failure. Encoding the feature as an atom
puts the decision in the capability system, where every other extension is modeled, and the
`spvAtomicFloat16VectorNV : ... + spvAtomicFloat16AddEXT` implication is what keeps
`InterlockedAddF16` from needing two user-facing spellings.

**Why the alias lost `| _spirv_1_0`.** That disjunct is the root cause named in the issue. With it,
`[require(GL_NV_shader_atomic_fp16_vector)]` was satisfied by any SPIR-V 1.0 target, so the
requirement was decorative. Replacing it with `| spvAtomicFloat16VectorNV` makes the alias require
the feature it is named after. This is the one intentionally user-visible behavior change: a shader
that previously type-checked against bare SPIR-V 1.0 now needs the capability. That is the point of
the issue — the old acceptance was unsound — and it is additive at the ABI level (no `include/`
enum, struct, or vtable change), so the PR is labeled `pr: non-breaking`, matching the label on the
previously attempted #11324.

**Why `getAtomicOperationValueType()` is shared instead of duplicated.** Three places now need the
atomic element type: SPIR-V legalize (to validate), IR validation (to diagnose), and emit (to
declare capabilities). Each needs the same `void`-return recovery. Duplicating that recovery is how
the three drift apart and start disagreeing about whether a given instruction is a fp16 vector
atomic — so it lives once in `slang-ir-util.cpp`.

*Is the `void`-returning input shape itself correct, or should its producer be fixed?* It is
correct, and deliberately so. The `out`-parameter form is the front-end contract for these
intrinsics, and legalization rewrites the instruction to `void` because SPIR-V's atomic ops return
their result differently. The pointer operand still carries the type, so nothing is lost — the
information is merely at a different operand than the naive reader expects. Fixing "the producer"
here would mean changing the meaning of legalized atomic instructions across the SPIR-V backend to
suit three consumers, which is the larger and less safe change. The helper documents the recovery
and keeps all three consumers honest.

**Why the unsupported cases are validation diagnostics, not emit-time guards.** `half3` atomics and
fp16-vector compare-exchange have no encoding in `SPV_NV_shader_atomic_fp16_vector`. Emitting
something and hoping is wrong, and asserting in emit turns a user error into a compiler crash.
Instead `validateSPIRVFp16VectorAtomicOperation` diagnoses them during SPIR-V legalization
(E50013 width, E50014 operation), and `emitSPIRVFromIR` now returns `SLANG_FAIL` when the sink holds
errors, so emit does not run on IR already known to be unrepresentable. The generic
`validateAtomicOperations(IRModule*, ...)` pass passes `false`, so non-SPIR-V targets are unaffected
— CUDA, for instance, has its own width rules and its own test case here.

**Why the `SLANG_RELEASE_ASSERT` in `ensureAtomicCapability` is an assert and not a diagnostic.**
On the `OpAtomicLoad` / `OpAtomicStore` / `OpAtomicCompareExchange` paths the code asserts the value
type is *not* a fp16 vector. That is only legitimate if user code cannot reach it, so the ordering
is load-bearing and worth stating explicitly: `emitSPIRVFromIR` calls `legalizeIRForSPIRV` →
`legalizeSPIRV` → `SPIRVLegalizationContext::processModule`, whose last action is
`validateAtomicOperations(..., /*validateSPIRVFp16VectorAtomics:*/ true)`. In the validator,
`AtomicCompareExchange` has its own arm and `AtomicLoad` / `AtomicStore` fall to the `default:` arm;
all three therefore diagnose E50014 for a fp16-vector operand. Control then returns to
`emitSPIRVFromIR`, which checks `sink->getErrorCount() != 0` and returns `SLANG_FAIL` *before* any
emit. So a user program with a fp16-vector compare-exchange produces a diagnostic and never reaches
the assert; the assert guards against a future IR pass synthesizing such an instruction internally,
which is a compiler bug and should be loud.

**Why capability registration moved before each emit.** `ensureAtomicCapability` was previously
called after `emitOpAtomic*`. Moving it before means capabilities are registered against IR that has
already passed validation, and keeps the ordering uniform across the Load/Store/Exchange/
CompareExchange/Add paths. Behavior for the existing scalar float32/float64 paths is unchanged —
`tests/spirv/` covers them.

**Why the atomic-sub negation is now explicitly serialized.** For `AtomicSub` the emitter negates
the operand and emits an atomic add. `builder.emitNeg(...)` creates the negation instruction but
does not place it in the SPIR-V output; without `emitLocalInst(parent, negatedOperand)` the atomic
add references an operand that was never emitted, producing invalid SPIR-V. The added call
serializes it into the enclosing block before use. `VECTOR_SUB`, `VECTOR4_SUB`,
`SCALAR_FLOAT_SUB`, and `SCALAR_DOUBLE_SUB` in the capability test cover this, the last two proving
the scalar float/double sub paths still behave as before.

**Why `hlsl.meta.slang` splits the `[require(...)]` per target.** `[require(cuda_hlsl_spirv, ...)]`
forced one requirement across three unrelated targets. Splitting into `[require(cuda_hlsl, sm_5_0)]`
plus a SPIR-V-specific requirement lets SPIR-V demand the atom it actually needs while CUDA/HLSL
keep theirs. `InterlockedAddF16` requires only the scalar `spvAtomicFloat16AddEXT` — which
`spvAtomicFloat16VectorNV` implies — so both kinds of target can call it; the new
`case spvAtomicFloat16VectorNV:` routes to the vector path with a lane-select on `byteAddress & 2`,
falling through to the scalar `OpAtomicFAdd` otherwise. `_NvInterlockedAddFp16x2` is inherently
packed-pair, so it requires `spvAtomicFloat16VectorNV` directly.

**Scope note.** Emitted call sites passing a `StorageBuffer` pointer argument now call
`requireVariableBufferCapabilityIfNeeded`. This was needed to make the pointer test cases in this PR
emit valid SPIR-V. It is deliberately limited to emitted call sites; the broader declaration-only
parameter handling is tracked separately in #11518, and the RHI feature gate that would let the
runtime `COMPARE_COMPUTE` cases run in CI is #11519.

## Risk

Blast radius is the SPIR-V atomic emit path plus the capability graph. The reordering touches all
atomic Load/Store/Exchange/CompareExchange/Add paths, which is why `tests/spirv/` is run as a whole
rather than just the new files. The `capdef` change requires the two auto-generated docs to be
regenerated, which this PR does from source. The intended user-visible change is that
`GL_NV_shader_atomic_fp16_vector` is no longer satisfiable by bare SPIR-V 1.0. Out of scope and
tracked separately: #11518 (declaration-only pointer parameter capabilities), #11519 (RHI feature
gate for the runtime cases).

Closes #11083.
