Fixes #11317.

## Motivation

`countof` on a fixed-size array returned the byte size of the array's *scalar
component* instead of the array's element count. Consider this program run
under `slangi`:

```slang
void main()
{
    int a5[5];
    double d5[5];
    uint16_t h5[5];
    int2 v3[3];
    printf("%d %d %d %d\n", countof(a5), countof(d5), countof(h5), countof(v3));
}
```

It printed `4 8 2 4` instead of the expected `5 5 5 3`. The values track the
scalar component size (`sizeof(int)==4`, `sizeof(double)==8`,
`sizeof(uint16_t)==2`, and `int2` → the scalar `int`'s `4`, *not* `sizeof(int2)==8`),
which is unrelated to the element count. The variadic-pack form
(`countof(values)` over `expand each T`) was already correct, so the defect was
specific to the array operand. The defect is in target-shared stages (AST→IR
lowering and IR specialization), so it affected every target, not just the
interpreter.

## Proposed solution

`countof` is semantically an *element-count* query. Its value should never flow
through the `NaturalSize` byte-layout machinery that backs `sizeof`/`alignof`.
The fix makes that true at both code-generation layers implicated in this bug
(semantic checking also handles `CountOfExpr`, via a separate constant-fold path
that is not implicated here):

1. In AST→IR lowering, stop taking the `NaturalSize::calcSize` constant-fold
   shortcut for a `CountOfExpr`, so `countof` always lowers to a
   `kIROp_CountOf` instruction and the count is computed by the pass that owns
   count semantics.
2. In the IR specialization pass, teach `maybeSpecializeCountOf` to fold a
   `kIROp_CountOf` over a fixed-size `IRArrayType` to its constant element
   count — the same single canonical fold path already used for type packs and
   tuples.

This keeps one source of truth for the count (the IR-specialize pass) instead of
duplicating a divergent, incorrect computation in the lowering shortcut.

## Concepts and vocabulary

- **`NaturalSize` / `ASTNaturalLayoutContext::calcSize`** — computes the byte
  `{size, alignment}` of a type under the scalar/natural data layout. It is the
  right source for `sizeof`/`alignof`, and carries no notion of element count.
  For a fixed-size array it returns the array's total byte size and the
  element's alignment; neither field is the element count.
- **`SizeOfLikeExpr`** — the shared AST base for `SizeOfExpr`, `AlignOfExpr`, and
  `CountOfExpr`. `visitSizeOfLikeExpr` lowers all three; the `else` branch (not
  `sizeof`, not `alignof`) is the `countof` case.
- **`kIROp_CountOf`** — the IR instruction representing an unresolved `countof`.
  `maybeSpecializeCountOf` in the specialization pass is the one place that folds
  it to a constant.

## Process report

**Layer 1 — the lowering shortcut fed `countof` the wrong quantity.**
`visitSizeOfLikeExpr` (`source/slang/slang-lower-to-ir.cpp`) begins by trying a
constant-fold shortcut:

```cpp
NaturalSize size{0, NaturalSize::kInvalidAlignment};
if (!sizeOfLikeExpr->dataLayoutType ||
    as<ScalarDataLayoutType>(sizeOfLikeExpr->dataLayoutType))
{
    ASTNaturalLayoutContext naturalLayoutContext(getASTBuilder(), nullptr);
    size = naturalLayoutContext.calcSize(sizeOfLikeExpr->sizedType);
}
```

`CountOfExpr` has no `dataLayoutType`, so the shortcut always fired for it. When
`size` is valid, the function returns at the bottom:

```cpp
const auto value = as<SizeOfExpr>(sizeOfLikeExpr) ? size.size : size.alignment;
return LoweredValInfo::simple(getBuilder()->getIntValue(resultType, value));
```

For a `CountOfExpr` this is neither `sizeof` nor `alignof` semantics — it returns
`size.alignment`. For `int[5]` that is `4`; for `double[5]`, `8`; for `int2[3]`,
`4` (the alignment of the scalar `int`). This exactly reproduces the observed
values. The variadic-pack form escaped the bug only because `calcSize` returns an
*invalid* `NaturalSize` for an abstract pack, so `size` was falsy and control
fell through to `emitCountOf`.

*Input-shape check:* is it correct for `countof` to reach the `calcSize`
shortcut at all? No. `calcSize` is a byte-layout computation; `countof` asks for
an element count, a different quantity that `NaturalSize` does not even model.
The shortcut path is valid for `sizeof`/`alignof` and should never have applied
to `countof`. The principled fix is therefore to exclude `CountOfExpr` from the
shortcut so it always lowers to `kIROp_CountOf`, rather than to add a third
count-from-`NaturalSize` case (which would keep count logic in the wrong layer):

```cpp
if (!as<CountOfExpr>(sizeOfLikeExpr) &&
    (!sizeOfLikeExpr->dataLayoutType ||
     as<ScalarDataLayoutType>(sizeOfLikeExpr->dataLayoutType)))
{
    ...calcSize...
}
```

**Layer 2 — a `kIROp_CountOf` over an array had no folder.**
Once Layer 1 makes `countof(int[5])` reach the IR as `kIROp_CountOf`,
`maybeSpecializeCountOf` (`source/slang/slang-ir-specialize.cpp`) is the only
place that folds it. It handled `kIROp_TypePack` / `kIROp_TupleType` (and their
`MakeValuePack` / `MakeTuple` value forms) but returned `false` for any other
operand, including `IRArrayType`. No emit backend has codegen for
`kIROp_CountOf` (the VM emitter's `emitInst` has no case for it and falls to its
`default: SLANG_UNIMPLEMENTED_X` at `slang-emit-vm.cpp`), so the op must be
folded before emission. Without Layer 2 an array `kIROp_CountOf` survives
unresolved and code generation fails rather than silently returning a wrong
value — which is why Layer 1 alone does not fix the bug, and why both layers are
required. The fix folds the array case through the same canonical mechanism used
for packs/tuples:

```cpp
if (auto arrayType = as<IRArrayType>(operand))
{
    if (auto count = as<IRIntLit>(arrayType->getElementCount()))
    {
        IRBuilder builder(module);
        builder.setInsertBefore(inst);
        auto newInst = builder.getIntValue(inst->getDataType(), count->getValue());
        addUsersToWorkList(inst);
        inst->replaceUsesWith(newInst);
        inst->removeAndDeallocate();
        return true;
    }
    return false;
}
```

*Input-shape check:* the operand is an `IRArrayType`, a canonical, intentional
shape here — `countof` accepts fixed-size arrays per the semantic checker, and
lowering (after Layer 1) deliberately emits `kIROp_CountOf` over that array type.
So this layer legitimately owns the fold; it is not patching a malformed shape.
The fold is guarded to fire only when the element count is a concrete
`IRIntLit`: a generic `T[N]` whose `N` is still a generic parameter has a
non-literal element count and must wait for a later specialization round (mirror
of the existing pack branch, which bails while any element is still abstract).
`IRUnsizedArrayType` never enters this branch — it does not match
`as<IRArrayType>` — so an unsized array is untouched by the fold.

Both changes are required and complementary: Layer 1 ensures the count reaches
the IR as a `kIROp_CountOf` instead of being mis-folded during lowering; Layer 2
ensures that instruction is folded to the correct constant. Removing either one
leaves the regression test failing.
